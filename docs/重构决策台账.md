## [D-001] `.bash` 是否算脚本

**背景**：`ls` 里 `.bash` 文件同样是可直接执行的 shell 脚本。
- 旧行为：只认 `.sh`
- 新实现：认 `.sh` + `.bash`

**默认决定**：**保留放宽**（认 `.bash`）

**理由**：
1. 用户开「只显示脚本」的目的是找「能执行的脚本」，`.bash` 完全符合
2. 过滤掉 `.bash` 会导致用户找不到真实存在的脚本，属于功能缺失
3. 已在 `LegacyEquivalenceTest` 显式记录为 documented tradeoff，差异可见不隐藏

**回滚方式**：删掉 `FileFilter.isShellScript` 里的 `.bash` 分支即可（单点改动）

## [D-002] `PathUtil` 的零调用纯函数是否接线

**背景**：`PathUtil.parent/join/fileName/isRoot/extension` 已实现且有测试，但生产代码零调用——`FilesFragment` 里仍用 `StringsKt.substringBeforeLast` 等内联调用。

**默认决定**：**接线**，把内联路径操作替换为 `PathUtil` 调用

**理由**：
1. 纯函数已单测覆盖，接线风险低
2. 消除散落各处的反编译内联调用，提升可读性
3. 是「新结构真正落地」的必要一步，否则又是一批孤岛

**风险与回退**：路径拼接是高频操作。若接线后出现路径错误，回退对应调用点为原内联写法（每个调用点独立，可逐个回退）

## [D-003] `DirHistory` 上限 60 条

**背景**：旧实现无上限（内存无限增长）。新实现加了 60 条上限，且根目录永久保留。

**默认决定**：**保留上限 60 + 根目录保留**

**理由**：
1. 无上限是内存泄漏隐患（长时间使用累积）
2. 60 条足够覆盖任何真实使用场景
3. 根目录保留保证「后退回根」永远可用

**已知副作用**：超过 60 条后最旧的非根目录会被淘汰，用户无法退到更早的目录。但这在真实使用中几乎不可能触发。

**回滚方式**：`DirHistory(maxEntries = Int.MAX_VALUE)` 即恢复无上限行为

## [D-004] Engine 拆分的契约风险

**背景**：评审报告警告两处契约会在拆分时断裂：
- `isAborted()` 依赖 `Thread.currentThread().isInterrupted()`（Engine:876）——换线程即失效
- `abort` 的 `pkill -f` 依赖 `currentScriptPath` 登记（Engine:66/911/1066）——拆到 RootShell 后契约断裂

**默认决定**：**先不拆 Engine 的执行部分**，只拆无契约依赖的纯逻辑

**理由**：
1. 违反契约会导致「停止关错进程」「停止无效」这类严重问题
2. 需要先设计 `ExecSession` 承载「线程中断状态 + 脚本路径 + 进程句柄」三者的生命周期，这是设计工作不是搬运
3. 在真机验证困难（Root 授权未通过）的情况下拆执行核心风险过高

**允许拆的**：
- `PromptMatcher`（应答匹配，纯字符串逻辑）
- `TermBuffer`（已拆，纯缓冲逻辑）

**暂不拆**：
- `RootShell`（su 执行 + abort 契约）
- `QueueState`（与 runningNow/RUNNING_GATE 强耦合）

## [D-005] 发现缺陷时的局部回退策略

**背景**：用户要求「修复出现问题，优先把出现问题的那部分结构回退到可用版本的那一部分」。

**默认决定**：**按模块粒度回退，不做全局回滚**

**执行方式**：
1. 每个模块独立 commit + tag
2. 出问题时 `git checkout <该模块的锚点> -- <相关文件>` 局部恢复
3. 保留已完成且验证通过的其他模块

**理由**：全局回滚会丢失已验证的成果，代价过高。

## [D-006] 真机 Root 授权

**背景**：dev 版是新包名，需在 KernelSU/Magisk 单独授权才能访问 `/data/adb`。

**默认决定**：**先做无 Root 可验证的部分**（`/sdcard` 路径、UI、单测），Root 相关功能等授权后验证

**理由**：不能因为一个外部依赖阻塞整体进度。

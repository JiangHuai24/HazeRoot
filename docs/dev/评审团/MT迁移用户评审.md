# MT 迁移用户评审报告：从 MT 管理器到 HazeRoot

> 评审立场：一名长期使用 MT 管理器的资深用户，肌肉记忆建立在「点按=打开、长按=多选、左滑=快捷操作、面包屑=跳转、双窗=跨窗操作」这套事实标准上。
> 评审依据：通读 `FilesFragment.java`（3380 行）、`item_file.xml`、`fragment_files.xml`，以及 `docs/dev/` 下《交互与实现改造规格》《技术根因诊断》两份一手文档。
> 结论一句话：**HazeRoot 的「文件管理」是照着 MT 的**样子**搭的，但没有照着 MT 的**手感**做；双窗骨架有了，肌肉记忆却在手势层和流程层被反复打断。**

---

## 一、手势对齐：点按/长按/左滑/多选，哪些地方会让我点错、误触

### 1.1 核心问题：四种手势挤在一个 500ms 的「自研状态机」里，且长按后还能继续变招

源码里 `bindSwipe()`（L1571 起）不是「点按走点击监听、长按走长按监听」的标准做法，而是给每一行的前景 `fgContent` 挂了一个 `OnTouchListener`，在 `ACTION_DOWN` 时 `postDelayed(longPress, 500L)` 启动一个 500ms 的长按定时器，随后在 `ACTION_MOVE` 里用 `mode` 字段在三个状态间手动迁移：

```
mode = 0  // 待定
mode = 1  // 左滑（reveal 快捷按钮）
mode = 2  // 长按后拖动 → 范围多选
```

**这对 MT 老用户意味着什么，我逐个对比：**

| 交互 | MT 里我会怎么做 | HazeRoot 里实际会发生什么 |
|---|---|---|
| **点按打开** | 手指落下抬起，秒开 | `ACTION_UP` 时先要判断 `longFired` 是否已触发、`mode` 是否等于 1/2；只要手指在 500ms 内没抬起、或横向位移超过 `slop`，点按就被吞掉转成左滑或多选 |
| **长按进多选** | 长按约 400ms，震动，进入多选并选中当前项 | `postDelayed(500L)` 是**硬编码 500ms**，比系统 `ViewConfiguration.getLongPressTimeout()`（通常 400ms 上下）慢一拍，且长按触发后 `mode` 仍是 0，必须再拖动才进入 `mode=2` 范围选择 |
| **长按后直接松手** | 进入多选 + 弹出批量操作 | L1730 分支：`longFired==true` 时松手会**弹单条 `fileMenu`**，而不是 MT 语义里「长按=多选」。**长按要么变菜单、要么变拖动选，唯独不是干净的多选** |
| **左滑** | 左滑该条 → 弹出单条快捷操作（删除/复制/移动） | 左滑是 `mode=1`，滑过 `maxSwipe/2` 才停住展开 4 个按钮（入队/复制/移动/删除），**松手不到一半会自动回弹**；这本身还行，但它和长按/点按抢同一个触摸流 |
| **多选模式下点按** | 切换选中 | 逻辑能走通（L1744 分支），但**前提是 `multiMode` 且 `selPane==rowPane`**，一旦左右两窗同目录、或左窗是右窗父目录，历史版本会命中错误窗格导致「点按无反应」 |

### 1.2 具体会让 MT 用户「点错/误触」的三个点

1. **长按 = 单条菜单，不是多选。** 这是最伤肌肉记忆的一处。MT 用户下意识「长按一个文件想批量删」，结果弹出来的是**这个文件的复制/移动/压缩/分享菜单**；要进多选，得长按后**再拖动**，或者去点左上角那排很小的 `multiBar` 按钮。规格书 E 节自己都写了「长按=进入多选并选中该项」是目标，但**当前实现没做到**——文档里的「HazeRoot 现状：有长按但逻辑乱」就是实锤。

2. **左滑展开的是「入队/复制/移动/删除」，MT 里左滑通常只有「更多」或直接删除。** HazeRoot 把 4 个按钮全堆在 192dp（`dp(48)*4`）的 reveal 区里，`fbEnqueue` 是 HazeRoot 特有概念，MT 用户第一反应是「这行字（入队）是什么、会不会误点」。而且 `fbDelete` 是红色、和其它按钮同级排在最右，**滚动/回弹时容易误触删除**。

3. **500ms 硬编码长按 + `dx > dy*1.2` 的左滑判定边界脆弱。** 斜着滑一点、或稍微慢一点，手势就在「左滑」和「拖动多选」之间摇摆。MT 的手势是系统级 GestureDetector，边界稳定；HazeRoot 是手写，`技术根因诊断`三.3.1 已经点名这是「历史 bug 的根因」。

## 二、双窗体验：骨架有了，手感不对

### 2.1 当前窗高亮：弱到几乎看不见

源码 `restylePanes()`（L460）：当前窗 `pathView` 用 `bg_pick_hint`，非当前窗用 `bg_quick_chip`。也就是说**「当前窗」的区分只落在 30dp 高的路径栏背景上，列表区（占屏 90%）两个窗完全一样**。`fragment_files.xml` 里 `listA`/`listB` 没有任何高亮属性。

**MT 里我会怎么做**：看哪个窗的列表有高亮描边 / 背景亮度高，一眼锁定「我现在操作的是哪边」。
**HazeRoot 里我现在要怎么做**：去盯顶部那条 11sp 的 monospace 路径栏哪个更深色，或者干脆靠「点一下」去试。

### 2.2 中缝：固定 1px，不能拖调

`fragment_files.xml` 双窗之间只有一条 `<View android:background="@color/divider" android:layout_width="1px">`，**没有任何拖拽把手**。规格书 B/E 两节都写了「中缝可拖调」是 MT 对齐项，但当前**完全没实现**。MT 里我习惯左窗 40% / 右窗 60% 自己拉；HazeRoot 里只能 50:50 锁死，长文件名在左窗会被截断到没法看。

### 2.3 跨窗复制/移动：方向感对，但「确认/目标窗」被省略了

源码 `multiCopyMove()`（L1269）：多选后点「复制/移动」，**直接 `otherOf(pane)` 当目标窗，无任何确认、无目标路径二次选择**。单条 `fileMenu` 的「复制到右侧窗/移动」也是同理，`copyMoveTo$default` 里 `pane2 = otherOf(pane)` 直接跳进后台线程 `cp -a` / `mv`。

**MT 里我会怎么做**：选文件 → 复制 → 到另一窗/指定路径 → 粘贴，有明确的两段式「源-目标」心理模型。
**HazeRoot 里我现在要怎么做**：复制动作点下去**立刻对另一窗执行**，我只知道「目标=另一窗当前目录」，但**另一窗当时停在哪？** 得切过去先确认。规格书 E 节自己写「现状：流程断裂」，指的就是这里：**没有「目标窗选择 + 确认」这一步**。

### 2.4 双窗同目录/父子目录的隐藏雷

`paneOfRow()` / `bindSwipe$paneOf()` 的注释（L1588、L1817）明确记录：历史版本用「路径前缀匹配」判断某一行属于哪个窗，左右同目录、或左窗是右窗父目录时会**误判窗格**，导致「点按无反应」「点空白弹新建」。当前改成了 `getPositionForView` 逐个探测，但这是**修 bug 补丁，不是设计**——MT 里双窗从来不存在这种「我点右窗结果它以为我点左窗」的隐患。

## 三、文件操作流程：哪一步和 MT 不一致、流程断裂

### 3.1 复制/移动：缺「粘贴」心智，且目标锁定为另一窗

见 2.3。MT 是「复制→粘贴」两段式；HazeRoot 是「复制=立即跨窗 cp」。对于「复制到本窗」的场景，源码走 `fileMenu` 里的「复制到此处」（`copy_here`），靠 `copyMoveTo(e, pane2, false, pane2)` 且 `self && !move` 时自动加 ` (1)` ` (2)` 后缀防覆盖——但**没有「重命名/覆盖/跳过」三选一**，MT 里同名冲突会弹选择框，HazeRoot 只会**静默加括号后缀**（L2418-2431）。

### 3.2 压缩：命名不可控，永远 `.tar.gz`，且目标是另一窗

`zipTo()`（L2541）硬编码输出为 `源名.tar.gz` 到 `otherOf(from)`；批量 `multiZip()`（L1341）输出为 `首项_batch.tar.gz`。**MT 里我会怎么做**：压缩时可选 zip/tar.gz/7z、可选压缩级别、可命名、可选密码。**HazeRoot 里我只能得到**：一个 `.tar.gz`，名字自动拼，目标默认另一窗。根因是底层直接调 `tar -czf`，没有 UI 封装。

### 3.3 解压：只认 4 种后缀，且只能解到当前窗所在目录

`isArchive()`（L2482）只认 `.tar.gz/.tgz/.tar/.zip`；`unzipTo()`（L2487）用 `-d dstDir` 解到 `from.getDir()`。**MT 里我会怎么做**：长按压缩包 → 解压 → 可选「解压到当前/解压到指定/解压到对侧」。**HazeRoot 里**：解压目标只有「当前窗目录」，没有 `unzip 到对侧` 的入口；且 `.7z/.rar` 直接不识别（`isArchive` 返回 false，菜单里连「解压」都不出现）。

### 3.4 删除：`rm -rf` 无回收站，不可逆

`deleteDialog$lambda$78`（L2938）直接 `rm -rf`，多选删除同理（L1545）。MT 有回收站/确认 + 根目录危险提示；HazeRoot 只有一个 `AlertDialog` 确认，**确认后彻底删除，无回收站、无恢复**。这对 root 用户尤其危险：误删 `/data/adb` 里的东西直接消失。

### 3.5 重命名：无后缀联动、无同名检测

`renameDialog$lambda$76`（L2880）只是 `mv` 原路径到新名，**没有检查目标是否已存在**（`mv` 会静默覆盖），也没有「只改主名、保留扩展名」的智能处理。MT 重命名会高亮主名、保留扩展名，HazeRoot 里 `inputEt(e.getName())` 是全名可编辑，**容易把 `.sh` 后缀删掉**。

### 3.6 APK 安装：流程能通，但多了一步「复制到暂存区」

`installApk()`（L2718）先检查 `canRequestPackageInstalls()`，然后**复制 APK 到应用 `share` 目录**（因为 root 下 `cp` 产物属主是 root，FileProvider 读不了），再 `startActivity(VIEW)`。MT 里点 APK 基本是**一步进系统安装器**；HazeRoot 里点 APK 会先弹「正在准备」Toast + 后台复制，多一次延迟。而且 `isApkFile()`（L2711）的正则 `.*\.?apk(\.\d+)?` 会把 `.apk.1` 这种也当 APK，**误判风险**。

## 四、长文件名 / 路径导航：够不够？

### 4.1 长文件名：`ellipsize=end` 会把关键后缀吃掉

`item_file.xml` 里 `fName` 是 `singleLine + ellipsize=end`。长名如 `Fuzz_Cheat_v4.1.sh` 会变成 `Fuzz_Cheat_v4...`，**`.sh` 后缀没了**。MT 老用户靠后缀瞬间识别文件类型，这里直接断掉。

`fMeta`（第二行）是 10sp monospace 单行，塞「权限串 · 大小」，**`ls -Al` 出来的权限串（如 `drwxr-xr-x`）本身就 10 个字符**，再加大小，稍长就截断。

**没有「点按/长按看全名」的兜底**：`技术根因诊断`二.2.3 已确认——`pathView` 有长按看完整路径，但**文件名本身**无任何展开交互。MT 里长文件名至少能横滑滚动或弹详情看全名。

### 4.2 路径导航：只有「文本框 + 上一级」，没有面包屑

`fragment_files.xml` 每个窗顶部是 `[‹ 上一级] [pathView 文本框]`，`pathView` 是 `singleLine + ellipsize=start`（从头部截断，显示尾部路径）。**MT 里我会怎么做**：点面包屑中间的某一级，直接跳回那一层。**HazeRoot 里我现在要怎么做**：只能点 `‹` 逐级往上，或长按 `pathView` 设 home、点 `pathView` 弹 `jumpDialog()` 手动输入路径（L810）。

`ellipsize=start` 意味着深路径只显示**最后几级**，看不到中间层级，无法像 MT 面包屑那样「一眼看清自己在哪、点中间跳转」。

### 4.3 结论：路径导航**严重不够**，长文件名**不够**。这两项是规格书 B.3 明确要改、但当前源码完全没动的。

## 五、类型图标 / 信息层级：能不能一眼识别？

源码 `bindList()` 的 `getView`（L1095）里图标判定逻辑：

```
是目录 → ic_dir
是 ELF（通过 head -c 4 探测 7f454c46）→ ic_elf
以 .sh 结尾 → ic_script
其他 → ic_file
```

### 5.1 能识别的

- **文件夹 vs 文件**：有 `ic_dir`，能分。
- **脚本 `.sh`**：有 `ic_script`，能分。

### 5.2 识别不出来的

- **APK 没有专用图标**：`isApkFile()` 只用于「点按后装 APK」的分流，**不参与 `bindList` 的图标选择**。APK 文件落进 `ic_file`，和普通文件一个样。规格书 E 节写「强化脚本/APK 徽标」，**当前 APK 徽标缺失**。
- **压缩包没有专用图标**：`.zip/.tar.gz` 同样落 `ic_file`。
- **媒体文件没有图标**：图片/视频/音频都 `ic_file`。
- **图标只有形状，没有颜色双编码**：规格书 B.2 说「颜色+图标双编码」，但 `item_file.xml` 里 `fBadge` 是 24dp 的 `ImageView`，源码只 `setImageResource`，**没有按类型着色**。
- **ELF 探测是异步的**：`probeElves()` 后台跑 `for f in *; head -c 4 ...`，探测完才 `refreshSel()` 换图标，**图标会「闪变」**（先 `ic_file` 后 `ic_elf`），且文件数 >200 时直接跳过不探测。

**结论**：图标能分出「文件夹/脚本」，但 **APK、压缩包、媒体三类 MT 用户一眼认的，HazeRoot 都认不出**，信息层级远达不到 MT 标准。

## 七、给作者的三条最高优先级建议

1. **先把手势状态机按规格书 C.1 落地**：把「长按=进入多选并选中该项」做成真语义，左滑只做「单条快捷操作」且删除移出 reveal 区；这直接解决 S 级前两项。
2. **双窗加「当前窗列表高亮 + 中缝拖调」**：这是 MT 用户视觉定位的锚点，成本低、收益高。
3. **复制/移动补「目标窗确认」这一步**：哪怕只是弹一个「复制到：左窗/右窗/当前目录」的三选确认框，也能把「流程断裂」补上。

## 附：MT 迁移结论

HazeRoot 在**终端/脚本队列**上是 MT 没有的差异化优势（这点是加分的），但**作为「MT 式文件管理器」的迁移目标，当前只有「双窗 + 列表 + 左滑 reveal」的形，没有「长按多选、CAB、面包屑、目标确认、类型图标、长名截断」的魂**。MT 用户上手 5 分钟内会在「长按」这个最基础的动作上被噎住，10 分钟内会在「复制到哪去了」上抓狂。**结论：离「无缝迁移」还有一段不短的距离，手势层和双窗反馈层是必须先补的两块。**

# HazeRoot 架构与代码质量评审报告

> 评审对象：HazeRoot（Android root 脚本执行器）
> 技术栈：Java 17（实际为 Kotlin 反编译产物，`/* compiled from: *.kt */`）+ AppCompat，全局单例 `Engine` 驱动，无 ViewModel/LiveData
> 评审视角：遗留代码治理、并发安全、性能、可维护性、可测试性
> 一手依据：`app/src/main/java/com/hazeroot/scriptrunner/` 全部 30 个 Java 文件 + `docs/dev/` 下 ARCHITECTURE / 技术根因诊断 / 工程化重构方案
> 结论先行：**这是一个「功能已跑通、结构已失序」的教科书级 God Object 遗留系统。最危险的四个雷（跨线程 `termBuffer` 无同步、`runningNow` 竞态、静态 `ArrayList` 跨线程读写、UI 线程同步调 su）都指向同一个根因——全局可变单例 + 裸线程 + 无分层。ARCHITECTURE 的拆分方向正确，但遗漏了「线程/执行器模型」和「静态单例消灭」这两个决定性事项。**

---

## 0. 总体判断（打分）

| 维度 | 评分（1–5） | 一句话 |
|---|---|---|
| 功能完整性 | 4 | root 探测/执行/解码/ANSI/队列/录制/文件管理/编辑器都做出来了，且注释显示作者反复修过真实 bug |
| 并发安全 | **1** | 4 个高危竞态，任意一个都能在真机上偶发崩溃或显示错乱 |
| 性能 | 2 | UI 线程同步 su、N+1 进程、TextView 全量重绘、整文件读入内存 |
| 可维护性 | 1 | 三巨头 1347/3380/1678 行，静态单例穿透所有层，改一处牵全身 |
| 可测试性 | 1 | 几乎零接缝，`Engine.INSTANCE` 静态 + `ProcessBuilder` 内嵌 + 主线程 Handler 内嵌，纯 JVM 单测无法落地 |
| 数据持久化 | 2 | 手写 JSON + SharedPreferences `apply()` 异步 + 静默吞异常，可丢数据 |

## 1. 并发安全（高危区）

### 1.1 `termBuffer`：无任何同步的跨线程 StringBuilder —— 最致命

**证据链：**

- `Engine.java:83`：`private static final StringBuilder termBuffer = new StringBuilder();`
- 写线程（执行线程）：`log()` / `logRaw()` 在 `runOne` 的读输出循环里被反复调用（`Engine.java:168-183`）。
- 读线程（主线程）：`QueueFragment.syncTerm()` 在 `Engine.java` 的 `emit("log")` 回调里执行 `Engine.INSTANCE.getTermBuffer().toString()`（`QueueFragment.java:827`，经 `QueueFragment$uiListener$1.java:106`）。

`StringBuilder` 不是线程安全的。执行线程在 `termBuffer.append(...)` 的**过程中**，主线程同时 `toString()`，会读到中间态（半行、半个 `\u0001` 标记、甚至触发 `ArrayIndexOutOfBoundsException` 级别的内部状态损坏）。这是「偶发显示不全/乱码」的根因之一，`docs/dev/HazeRoot-技术根因诊断.md:1.3` 也已确认，但评审要强调：**这不是可接受的「偶发」，而是每次高输出频率下都有概率触发的数据竞争（data race）**。

### 1.2 `trimTerm()` 按 char 裁剪，切断 `\u0001 + styleChar` 标记对

**证据：** `Engine.java:185-189`

```java
private final void trimTerm() {
    if (termBuffer.length() > MAX_TERM_CHARS) {          // 200000
        termBuffer.delete(0, termBuffer.length() - MAX_TERM_CHARS);
    }
}
```

`termBuffer` 内混有两类内容：
1. 纯文本（含中文等多字节解码后的 UTF-16 char）；
2. ANSI 样式成对结构 `\u0001` + 单个 styleChar（`log()` 第 172 行 `termBuffer.append((char)1).append(style)`）。

`delete(0, ...)` 只按 char 计数裁剪，**裁剪点完全可能落在 `\u0001` 和它的 styleChar 之间**，产生一个孤立的 `\u0001`。后续 `appendStyled`（`QueueFragment.java:896-911`）按 `charAt(i)==1 && i+1<length` 成对消费标记，一旦出现孤立标记，**整条增量渲染从该点开始全部错位**——这就是技术根因诊断 1.1 描述的「显示不全/丢行」的精确机制。

**评审补充**：诊断文档认为 `Kt.contains(dst, '\u0001')` 兜底「从未生效」，评审同意——正常路径 `appendStyled` 已把标记剥离，`dst` 里永远不会有 `\u0001`，所以这个判断是**死代码兜底**，不能指望它救场。真正的修法是把裁剪改到「行边界 + 标记对边界」上，见 Top 10 #1。

### 1.3 `runningNow` 的 check-then-act 竞态（双跑）

**证据：** `Engine.java:546-557`

```java
public final void runQueue(...) {
    if (runningNow) { Log.d(...); return; }   // 550 检查
    abortFlag = false;
    runningNow = true;                        // 555 置位
    ...
}
```

`runningNow` 是 `volatile boolean`（`Engine.java:73`），但「检查 + 置位」不是原子操作。两个调用方（`QueueFragment.doStartQueue` / `PresetsFragment` 运行方案 / `FilesFragment` 直接执行）都可能各自在后台线程触发 `runQueue`。两个线程可同时通过第 550 行的检查，然后都进入执行 → **两个执行线程同时跑队列、同时写 `termBuffer`、同时抢 `currentProc`**。

**修法**：`AtomicBoolean.compareAndSet(false, true)` 做门禁，或把「是否运行中」并入显式 FSM（`ExecutionState`）由单点 `ExecutionCoordinator` 推进。

### 1.4 `currentProc` 非 volatile，跨线程读写

**证据：**

- 写：`Engine.java:894` `currentProc = proc;`（执行线程）
- 读：`Engine.java:800-818` `abort()`（UI 线程）、`Engine.java:218` `sendRaw()`（UI 线程）
- 声明：`Engine.java:62` `private static java.lang.Process currentProc;` —— **没有 volatile，没有同步**。

Java 内存模型下，非 volatile 字段的写入可能对另一线程不可见。`abort()` 可能读到一个过期的 `currentProc`（null 或旧进程），**停止按钮关错进程**；`sendRaw` 也可能把输入写进上一个进程的 stdin。这是「停止/手动输入偶发失效」的候选根因。

### 1.5 `scripts` / `presets` 静态 `ArrayList` 跨线程读写无锁

**证据：**

- 声明：`Engine.java:75-76` `private static final List<ScriptItem> scripts = new ArrayList();`（非线程安全）
- 写（UI 线程）：`QueueFragment.addScriptByPath:737`、`editScriptDialog$lambda$53`、`QueueFragment$onViewCreated$3:47`（删除）、移动脚本 `onViewCreated$2:218-222`
- 读/迭代（执行线程）：`runQueue` 的 `for (ScriptItem s : list)`（`Engine.java:587-658`），且 `runOne` 内还调用 `Store.saveScripts(appCtx, scripts)`（`Engine.java:645`）

UI 在执行期间删/移脚本，执行线程同时迭代同一 `ArrayList` → **`ConcurrentModificationException` 直接崩溃**，或迭代到不一致状态。诊断文档 4.1 只提「入队缺反馈」，没点出这个崩溃级竞态。

**修法**：`scripts`/`presets` 换成 `CopyOnWriteArrayList`（写少读多、体量小），或更彻底地收敛到 `QueueRepository` 单写者模型（ARCHITECTURE 的方向是对的）。

### 1.6 `SU_LOCK` 的注释是假的——并未串行化所有 su 调用

**证据：** `Engine.java:69-72` 注释声称「所有 su 调用串行化」，但：

- `su()`（`Engine.java:410`）和 `execBytes()` 的 su 分支（`Engine.java:484`）确实在 `synchronized (SU_LOCK)` 内；
- **但** `checkRoot()`（`Engine.java:263` 直接 `new ProcessBuilder("su","-c","id")`）、`runOne` 的探测（`Engine.java:845`）、`hasBusyboxScript()`（`Engine.java:779`）**都绕过 `SU_LOCK` 直接起 su 进程**。

所以「文件页两窗并行加载 + ELF 探测会同时发起多个 su」这个原始问题（注释里写的动机）**并没有被 `SU_LOCK` 真正解决**——`FilesFragment.Pane.load` 的 `Engine.exec("ls -Al ...")` 会走 `su()` 被串行，但 `probeElves` 的 `Engine.exec` 也走 `su()` 串行……真正的漏洞是 `checkRoot` 和 `hasBusyboxScript` 以及 `runOne` 的预探测直接起进程。**锁的覆盖范围与注释承诺不一致**，属于「看似修了、实则留了后门」的隐患。

## 2. 内存 / 性能（会埋雷的点）

### 2.1 `execBytes("cat ...")` 整文件读入内存（OOM 雷）

**证据：** `EditorActivity.java:327` 调用 `Engine.INSTANCE.execBytes("cat " + q(str))`，`Engine.execBytes` 用 `ByteStreamsKt.readBytes(inputStream)`（`Engine.java:491`）一次性读完全部字节，再在 `EditorActivity` 里截断到 512KB（`EditorActivity.java:340-360`）。

**问题**：文件本身如果是 1GB/2GB 的 ELF 或数据文件，`readBytes` 会**先把整个文件装进堆内存**，然后才截断。这是「打开大文件编辑器闪退/黑屏」的直因。文件页 `detailDialog` 判断 ELF 也只 `head -c 4`（`isElf`，没问题），但编辑器读内容是 `cat` 全量。

**修法**：改为 `head -c 524288` 或流式读 + 限制读取量，绝不在 su 侧全量读文件。

### 2.2 每文件一次 su 进程（N+1 进程开销）

**证据：**

- `FilesFragment.multiCopyMove$lambda$28` / `multiDelete$lambda$34$lambda$33`（`Engine.exec` 在 for 循环内逐条执行，`FilesFragment.java:1294` / `1543-1545`）
- `sharePaths$lambda$49`（`FilesFragment.java:1988-2034`）每个路径一次 `Engine.exec`
- `copyMoveTo$lambda$53` 每次一次 `cp/mv`

每个 `exec` 都是一次 `su -c sh -c '...'` 的**完整进程启动**（几十毫秒）+ 被 `SU_LOCK` 串行。选 100 个文件复制就是 100 次串行 su。慢且高并发触发 KernelSU 拒绝（注释里自己都写了）。**修法**：合并为单条 `sh -c` 批处理命令。

### 2.3 `trimTerm` 后的全量重绘 + Spannable 全量重建（掉帧雷）

**证据：** `QueueFragment.syncTerm:842-859`

```java
if (buf.length() < this.renderedChars) {
    this.renderedChars = 0;
    dst.clear();                 // 全量清空
}
if (buf.length() > this.renderedChars) {
    if (this.renderedChars == 0) dst.clear();
    ...
    appendStyled(dst, substring);   // 从 0 开始全量重建
}
```

每次 `trimTerm` 裁剪头部后，`buf.length() < renderedChars` 成立 → `dst.clear()` 后从 0 全量重绘一个最多 20 万字符的 TextView，且 `appendStyled`（`QueueFragment.java:896-911`）**逐字符扫描 + 每个样式段新建一个 `ForegroundColorSpan` 对象**。20 万字符 + 高频 ANSI 样式 = 数万个 Span 对象 + O(n) 主线程重建 = **单帧远超 16ms 的卡顿**。这与 ARCHITECTURE §4「行级脏标记 + 可见行全量重绘」的目标背道而驰——现状是「字符级 Span + 整块全量重绘」。

### 2.4 `emit("log")` 无帧合并，高频事件打爆主线程

**证据：** `Engine.log/logRaw` 每次 append 都 `emit("log", ...)`（`Engine.java:176,182`），`emit` 每次 `main.post` 一个 Runnable（`Engine.java:126-133`）。脚本高频输出时（如 `yes`、循环 echo），**每秒可能 post 数百上千个主线程任务**，每个任务里 `syncTerm` 又做字符串 `substring` + `appendStyled` 遍历。没有 Choreographer/Handler 帧合并（coalesce）。

ARCHITECTURE 1.4.3 明确要求「帧合并」，但这是目标而非现状。**现状 = 高频输出时主线程队列被 log 事件淹没**，是「长跑脚本 UI 卡死」的机制之一。

### 2.5 频繁 String 拼接

**证据（典型）**：

- `Engine.q()`（`Engine.java:400-403`）每次 `'` + replace + `'`，且 `su()` 里 `"su","-c","sh -c " + q(cmd)` 层层拼接；
- `FilesFragment` 里 `StringsKt.trimEnd(newDir,'/') + "/" + name` 在解析循环内反复（`FilesFragment.java:913`）；
- `MainActivity.downloadTo$lambda$25$lambda$24` 里 `"mkdir -p " + q + " && cp " + q + ...`（`MainActivity.java:736`）。

对低频率路径影响有限，但对高频解析（`ls` 输出逐行、ELF 探测 shell for 循环）会造成 GC 压力。属「次要但可顺手修」级别。

### 2.6 FilesFragment 后台线程 `gen` 防乱序——方向对但**不取消**

**证据：** `Pane.load` 里 `this.gen++` 后 `final int g = this.gen`（`FilesFragment.java:844-846`），回主线程时 `if ($g == this$1.gen)`（`FilesFragment.java:945`）丢弃过期结果。

**评审结论**：`gen` 版本号防乱序是**正确的、值得肯定的做法**。但它只防「旧结果覆盖新结果」，**不取消旧线程**——旧线程仍会继续 `Engine.exec("ls -Al ...")`（一次 su 进程）并占住 `SU_LOCK` 排队。快速连续跳转 10 个目录 = 10 个旧 su 进程照样跑完，纯浪费 + 串行阻塞新请求。修法：配合 `ExecutorService` + `Future.cancel` 或至少让过期的后台任务在拿到锁后先自检 `gen` 再执行 su。

## 3. God Object 拆分评估（ARCHITECTURE 合理性）

### 3.1 拆分方向正确，映射表基本合理

ARCHITECTURE §8 把 `Engine` 9 帽拆成 core 8 类 + domain 1 用例、`FilesFragment` 6 帽、`QueueFragment` 4 帽，**拆分粒度与归属包划分是对的**，与 `docs/dev/工程化重构方案` 2.3 一致。特别是「绞杀者 + 按抽象分支 + Feature Toggle」「先插接缝再动结构」「先补特性测试锁行为」这三点，是正确且成熟的做法。

### 3.2 关键遗漏一：没有「线程/执行器模型」

ARCHITECTURE §2-§8 拆出了 `ChunkReader`、`Watchdog`、`SessionRecorder`、`ExecutionQueue` 等类，但**通篇没有定义谁拥有线程、线程如何创建/取消/回收、并发模型是什么**。现状是：`runQueue` 一个裸线程、`runOne` 里 per-item 再开 `silence` 看门狗线程、`FilesFragment` 每个目录导航一个裸线程、`probeElves` 又一个裸线程——全是 `new Thread` 无池无生命周期。

拆分后如果每个新类继续 `new Thread`，God Object 是拆开了，但**线程地狱原样迁移**。必须在拆分前定义 `ExecutionScope`（或 Kotlin coroutine scope / `ExecutorService`）作为 core 层一等公民，所有异步任务走它，`ChunkReader`/`Watchdog` 都是它的子任务。**这是评审认为当前文档最大的架构级遗漏。**

### 3.3 关键遗漏二：没有「消灭静态单例」的硬门禁

ARCHITECTURE §0 原则 4 讲「接缝优先」，§2.3.1 提「DI 根」，但**没有把「禁止 `Engine.INSTANCE` / `Store.INSTANCE` 静态直调」列为可校验的硬规则**。现状是 `Engine.INSTANCE` 被 `QueueFragment`、`FilesFragment`、`PresetsFragment`、`MainActivity`、`EditorActivity`、`MediaActivity`、`RunnerService` 直接引用（grep 全项目 `Engine.INSTANCE` 出现 100+ 次）。

只要 `Engine.INSTANCE` 还在，`domain` 禁 `android.*`、`core` 禁上层依赖这些 ArchUnit 规则就形同虚设——因为 UI 层直接跳过 domain/data 摸到 core 的单例。**拆分类之前必须先切断「静态单例穿透」**，否则拆出来的类依然被静态耦合，测试性得不到任何改善。

### 3.4 拆分顺序建议：终端专项应该「提取 + 表征 + 修复」原子化

里程碑是 M2（拆 Engine）→ M3（终端渲染专项）。评审认为：终端解码/ANSI/缓冲是**用户最痛且风险最高**的一块，且「拆分」与「修复」高度耦合——把 buggy 的解码逻辑先拆出来（M2）再用 Toggle 双轨跑（M2 验收是「行为等价」），意味着 **M2 会把当前的 bug 当作「待锁定的行为」固化进特性测试**，M3 再去改。风险是特性测试锁住的是**错误行为**，M3 改对后测试要返工。

更优顺序：**M1（插接缝+补测试）→ 直接把「终端解码/ANSI/缓冲」作为一个整体「提取 + 特性化 + 修复 + 回归」的原子里程碑先做**（因为它既是正确性修复又是可测试性收益最大的一块），再回头做 Engine 其余部分的纯结构拆分。纯结构拆分的风险低，可以放后。

### 3.5 其他遗漏/不一致

1. **`TerminalBuffer` 归属矛盾**：§2 表里放 `domain/model`，§8 又放 `core/io`。应唯一归属 `core/io`（它是纯数据 + 无 android 依赖），`domain/model` 只留业务实体。
2. **进程级可变静态量未映射**：`currentProc`、`abortFlag`、`runningNow`、`busyboxScriptOk` 这些进程级状态在 §5 FSM 里没有对应的拥有者。FSM 只建了「队列项状态」，没建「执行会话/进程生命周期状态」。应新增 `ExecutionSession` 状态机（`STARTING→RUNNING→WAITING_INPUT→COMPLETED/STOPPED/FAILED`）并让 `currentProc` 归 `ExecutionSession` 持有。
3. **`AppEventBus` 未与现有 `Engine.Listener`/`emit` 衔接**：§6 引入 `AppEventBus` 单例，但现状 `Engine` 已有一个 listener/emit 机制（`Engine.java:88-144`）。文档没说明 `Engine.Listener` 是废弃、封装还是迁移，也没定义事件**背压/合并**策略（见 2.4）。高频 `log` 事件直接搬到 AppEventBus 会同样打爆主线程。
4. **`resolveAnswer` 死方法未处理**：`Engine.java:1344-1346` 返回 null 的空实现，说明「应答规则匹配」这条接缝其实已预留但没实现。拆分时应明确 `AnswerRuleMatcher` 是「新实现」而非「迁移既有逻辑」。
5. **测试策略缺「并发/竞态」专项**：工程化方案 1.6.3 的测试金字塔覆盖解码/ANSI/FSM，但**没有针对 1.1-1.6 这些竞态的并发压力测试**。对遗留代码治理，这是必须补的一块，否则竞态重构无回归保护。

## 4. 数据持久化（Store + Json）隐患

### 4.1 SharedPreferences `apply()` 异步写 + `System.exit(0)` = 丢数据

**证据链：**

- `Store.saveScripts/savePresets` 用 `.apply()`（`Store.java:43,56`）——异步落盘；
- `Engine.finalizePreset` 收尾时 `Process.killProcess(Process.myPid()); System.exit(0);`（`Engine.java:759-760`）硬杀进程；
- 执行过程中每次脚本结束都 `Store.saveScripts(appCtx, scripts)`（`Engine.java:645`）。

`apply()` 是异步的，`System.exit(0)` 不保证 flush。**「执行方案后自动收尾退出」这条路径存在丢失最后一次 `saveScripts` 写入的真实风险**，表现为「跑完方案后队列状态/录制结果偶发回退」。

### 4.2 手写 JSON 全量序列化 + 静默吞异常

**证据：**

- `Json.scriptsFromJson`（`Json.java:52-66`）：`catch (Exception e) { }` **静默吞掉一切解析异常**，返回（可能不完整的）list；
- `Json.presetsFromJson`（`Json.java:125-152`）：同样 `catch (Exception e) { }`；
- `Json.scriptFromJson`（`Json.java:68-94`）反而 `throw new RuntimeException(e)`。

**不对称的错误处理**：**读**（`scriptsFromJson`）吞异常、返回空/半成品，**写**（`scriptsToJson` 第 48 行、`scriptFromJson` 第 92 行）抛 RuntimeException。结果：本地存储损坏时，用户**无任何提示**地被静默清空队列/方案，且没有任何日志定位。这是「数据无故丢失」的隐患。

### 4.3 全量序列化性能

`saveScripts` 每次把**整个 scripts 列表**序列化成一个 JSON 字符串再写（`Store.java:43` → `Json.scriptsToJson` 遍历全列表）。任何单条增删改都触发 O(n) 全量序列化 + 全量重写。数据量小（几个脚本）时无所谓，但**结构上不具备可扩展性**，且与 `scripts` 的跨线程竞争叠加（见 1.5）会让「执行线程保存」与「UI 线程修改」同时序列化同一个列表。

### 4.4 `deepcopy` 用 JSON round-trip 做深拷贝

**证据：** `Json.deepcopy`（`Json.java:155-158`）= `scriptFromJson(scriptToJson(s))`。

用序列化做深拷贝**功能上可用**（`recordedInputs` 都是纯字符串），但：
1. 每次方案保存对每个脚本做一次 JSON 序列化 + 反序列化，O(n) 且创建大量临时对象（`PresetsFragment.java:117-122` 对每个 script `deepcopy`）；
2. `scriptFromJson` 的 RuntimeException 会顺着 `deepcopy` 传播到 `savePreset`，导致「保存方案」偶发崩溃；
3. 语义上「深拷贝」不该依赖「可 JSON 化」这个隐含前提——将来 `ScriptItem` 增加非 JSON 字段（如 `File`、回调）就会静默丢字段。

**修法**：给 `ScriptItem`/`Preset` 写显式 `copy()`（或 clone），不要借道 JSON。

## 5. 可测试性分析（接缝应插在哪）

### 5.1 当前无法单测的耦合点（按阻断程度排序）

| 耦合点 | 证据 | 阻断后果 |
|---|---|---|
| `Engine.INSTANCE` 静态单例 + `appCtx` 静态 | `Engine.java:74,60`；全项目 100+ 处 `Engine.INSTANCE` | 任何 domain 逻辑都无法脱离 Engine 单测 |
| `ProcessBuilder` 内嵌 | `Engine.java:263,417,467,488,779,845,881` | su/exec 无法注入 Fake，测试必然起真进程 |
| 主线程 `Handler` 内嵌 | `Engine.java:78` `new Handler(Looper.getMainLooper())` | `emit` 强绑 Android Looper，纯 JVM 测不了 |
| `Store.INSTANCE` + `SharedPreferences` | `Store.java:16,24-26` | 数据层无法用内存 Fake 替换 |
| `System.currentTimeMillis()` 看门狗计时 | `Engine.java:1104,559,717` | Watchdog 无法做「快进时间」测试 |
| `Charset.forName("GBK")` / `StandardCharsets` | `Engine.java:1280,273` | 解码逻辑其实**可测**，但被压在 Engine 里无法隔离 |

### 5.2 最优先的三个接缝（按收益排序）

**接缝 1（最高优先）：`ProcessExecutor` / `SuGateway` 接口**

把 `ProcessBuilder` 的 `start()` 抽象出去，`Engine` 依赖接口而非直接 new 进程。这是 Michael Feathers 定义里最标准的 Seam——**无需改行为即可注入 Fake**。`SuGateway`（ARCHITECTURE §3 已定义）必须**覆盖** `checkRoot`/`hasBusyboxScript`/`runOne` 预探测这三个当前绕过 `SU_LOCK` 的裸 `ProcessBuilder` 点，而不是只包 `su()`。

**接缝 2：`Dispatcher`/`Clock` 抽象**

`emit` 的 `main.post` 和看门狗的 `System.currentTimeMillis()` + `Thread.sleep` 抽成 `Dispatcher.post(Runnable)` 和 `Clock.now()/sleep()`。这样 `ExecutionCoordinator`、`Watchdog`、`PromptDetector` 能在纯 JVM + 虚拟时钟下做确定性测试（不用真等 30 秒 IDLE）。

**接缝 3：`ScriptStore`/`PresetStore` 仓库接口 + 内存实现**

`Store` + `Json` 抽成 `QueueRepository`/`PresetRepository`（ARCHITECTURE 已定义），内存 Fake 用于测试，SharedPreferences 实现只做落盘。这同时解决 1.5 的竞态（收敛到单写者）和 4.2 的静默吞异常（在仓库层统一打日志 + 备份）。

### 5.3 一句话

**「先消灭 `Engine.INSTANCE` 静态直调」是可测试性的一票否决项。** 接缝插得再好，只要业务代码还在 `Engine.INSTANCE.su(...)`，单测就永远要真 root 真进程。DI 根 + 构造注入必须先于/同步于拆类落地。

## 6. 技术债 Top 10（按「不改会爆」严重度排序）

> 每条给出：文件+行号 → 问题 → 具体修法。

### #1 跨线程 `termBuffer` 无同步 + `trimTerm` 切断标记对（数据竞争 + 渲染错位）

- **位置**：`Engine.java:83,168-189`；`QueueFragment.java:826-911`
- **问题**：执行线程写、主线程读同一个非线程安全 `StringBuilder`；裁剪按 char 可能切断 `\u0001+styleChar` 标记对，孤立标记使增量渲染整体错位，表现为「显示不全/乱码/丢行」。
- **修法**：抽出 `TerminalBuffer` 类（行级环形缓冲 + 脏行标记），裁剪严格按**行边界 + 标记对边界**；写入侧单线程化（ChunkReader 单写者），UI 侧只读 `snapshot()`/增量 diff；`MAX_TERM_CHARS` 裁剪落在行首。这是最高优先级，先于一切拆类。

### #2 `runQueue` check-then-act 竞态 + `currentProc` 非 volatile（双跑 / 关错进程）

- **位置**：`Engine.java:62,73,546-557,894,800,218`
- **问题**：`runningNow` 检查与置位非原子 → 双线程并发执行；`currentProc` 无 volatile → `abort`/`sendRaw` 可能操作过期进程。
- **修法**：`AtomicBoolean.compareAndSet` 做执行门禁；`AtomicReference<Process>` 持 `currentProc`；把进程句柄归入 `ExecutionSession`，FSM 显式化「会话状态」。

### #3 静态 `scripts`/`presets` `ArrayList` 跨线程读写无锁（崩溃）

- **位置**：`Engine.java:75-76`；写侧 `QueueFragment.java:737,218-222`、`QueueFragment$onViewCreated$3.java:47`；读侧 `Engine.java:587-658,645`
- **问题**：UI 删/移脚本与执行线程迭代同一列表 → `ConcurrentModificationException`。
- **修法**：`CopyOnWriteArrayList`（短期止血），长期收敛到 `QueueRepository` 单写者 + 不可变快照。

### #4 `execBytes("cat")` 整文件读入内存（OOM）

- **位置**：`EditorActivity.java:327` + `Engine.java:480-526`
- **问题**：编辑器打开大文件先 `cat` 全量读入堆再截断，1GB+ 文件直接 OOM/黑屏。
- **修法**：改用 `head -c N`（限 512KB/1MB）或流式分块读 + 达到阈值即停。

### #5 UI 线程同步调 su（ANR）

- **位置**：`QueueFragment.java:1588`（`isElf`）、`FilesFragment.java:2844,2859`（`openEditor`/`detailDialog`）、`FilesFragment.java:2880-2895,3015,3315`（rename/new/chmod 的 `Engine.exec`）、`MainActivity.java:581`（`confirmOverwrite` 的 `Engine.su`）
- **问题**：这些调用在主线程同步起 su 进程（几十毫秒~秒级），慢 root 链路或 KernelSU 授权弹窗时直接 ANR。
- **修法**：全部切到后台 executor + 主线程回调；`isElf` 结果缓存（`Pane.elfMap` 已存在，可复用）。

### #6 `bindSwipe` 手势状态机 + 共享 `gestureBusy` + 行回收 Runnable（虚影/闪退）

- **位置**：`FilesFragment.java:81,1571-1800`
- **问题**：`mode`/`longFired`/`downX` 等 Ref 状态随 ListView 行回收而错乱；`v.postDelayed(longPress,500)` 的 Runnable 在行被回收后仍可能触发；`gestureBusy` 是 Fragment 级共享字段，多指触摸互相污染。这是历史「虚影/闪退」的结构性根源。
- **修法**：抽独立 `GestureController`（坐标快照，不捕获 row 引用），`onTouch` 内用 `MotionEvent` 坐标判定，长按 Runnable 随 View detach 取消，`gestureBusy` 改为按行状态。

### #7 SharedPreferences 手写 JSON + `apply()` 异步 + 静默吞异常（丢数据）

- **位置**：`Store.java:40-57`、`Json.java:52-66,125-152,92`、`Engine.java:759-760`
- **问题**：`apply()` 异步 + `System.exit(0)` 硬杀 = 可能丢最后写入；JSON 解析异常静默吞 = 损坏无提示被清空。
- **修法**：关键保存改 `commit()`（或 Room/文件原子写 + rename），解析异常打日志 + 保留原值备份，统一错误处理语义。

### #8 每文件一次 su 进程（N+1 慢 + 高并发触发 KSU 拒绝）

- **位置**：`FilesFragment.java:1294,1543-1545,1988-2034,2411-2440`
- **问题**：批量复制/删除/分享逐文件 `Engine.exec`，每个都是独立 su 进程且被 `SU_LOCK` 串行，百级文件慢到不可用。
- **修法**：合并为单条 `sh -c` 批处理（cp/mv/rm 一次打包），`SU_LOCK` 内一次调用完成。

### #9 `finalizePreset` 里 `System.exit(0)` 硬杀进程（崩溃式退出）

- **位置**：`Engine.java:759-760`
- **问题**：收尾时 `Process.killProcess` + `System.exit(0)` 直接杀进程，不做 flush、不释放资源、不走 Activity/Service 生命周期，与 #7 叠加导致丢数据，且日志里毫无 graceful shutdown 痕迹。
- **修法**：改用 `finishAndRemoveTask()` 让 Activity 自然结束，Service 在 `done` 事件里 `stopSelf()`（`RunnerService` 已有此逻辑），彻底删除 `System.exit(0)`。

### #10 `emit("log")` 无帧合并 + TextView 全量重绘（主线程打爆）

- **位置**：`Engine.java:126-183`、`QueueFragment.java:826-911`、`QueueFragment$uiListener$1.java:106`
- **问题**：高频输出时每秒数百上千个 `main.post`，每个都做 `substring` + 逐字符 `appendStyled` + Span 重建，主线程队列被淹没，掉帧。
- **修法**：Choreographer/Handler 帧合并（一帧内累积增量只 apply 一次），渲染改行级脏标记 + `notifyItemRangeInserted`（队列页）或可见行重绘（终端页），Span 合批。

# HazeRoot 终端与脚本执行体验评审报告

> 评审人视角：root 脚本重度用户 / 进阶玩家
> 每天在 Android 上用 root 跑 shell/ELF（内核模块、驱动、卡密验证、长跑守护、PTY 交互脚本），日常工具是 MT 管理器 + Termux。
> 评审对象：HazeRoot（通用 root 脚本执行器）
> 一手证据：`Engine.java`（1347 行）、`QueueFragment.java`（1678 行）、`PresetsFragment.java`、`ScriptAdapter.java`、`Json.java`、`docs/dev/` 下 PRD / 技术根因诊断 / 交互改造规格。

---

## 0. 一句话结论

HazeRoot 的**产品定位是对的**（把"手动敲回答"变"点一下跑完"），但当前实现是一个**"能跑起来、但不能算好用的终端"**：终端渲染是"流式 TextView + Spannable 拼色"而非真正的终端模拟器，录制→方案→重放的闭环**在代码层面是断的**，队列是"一次性执行器"而非"任务队列"，停止不杀子进程、ELF 不走 shebang、`\r` 覆盖进度条完全坏掉。它离"每天都要用"还差一个 P0 档的终端内核重建。

## 1. 终端显示

### 1.1 "sh 显示不全"根因：我认同大半，但诊断文档漏了三处更致命的

《技术根因诊断》把根因锁定为：①环形缓冲 `trimTerm()` 按 char 裁剪可能切在 ANSI 标记 `\u0001+style` 中间；②`renderedChars`（带标记长度）与 `dst`（去标记长度）游标错位；③`StringBuilder` 跨线程读写竞争。**这三点我认**，`QueueFragment.syncTerm()` 里 `renderedChars` 与 `dst` 各自自洽但不可互比、`Kt.contains(dst,'\u0001')` 兜底永远不生效（`appendStyled` 已去标记），都是实锤。

但作为天天看脚本输出的人，我要补三个诊断文档没写的**更致命问题**：

| # | 源码证据 | 真实症状 |
|---|---|---|
| A | `Engine.java:941` `boolean pendingCr` 被赋值 4 次（1006/1011/1015 行），但**从未被读取** | `\r` 回车符被直接吞掉，**覆盖式进度条彻底坏掉** |
| B | `Engine.java:1189-1253` `feedAnsi()` 的 CSI 状态机只认 `m`（SGR），`H/J/K/A/B/C/D/G` 全部 `esc=0;csi.clear()` 丢弃 | `\033[2J` 清屏、`\033[G` 光标回行、进度条刷新全变成垃圾 |
| C | `Engine.java:1313` GBK 分支排在 `1325` UTF-8 双字节分支**之前**，`0xC2–0xDF` 既是 GBK 首字节又是 UTF-8 两字节首字节 | 混合编码块里 UTF-8 的 À–ß 被 GBK 优先误读 |

### 1.2 场景 + 痛点 + 期望

**场景 1：跑一个带 `\r` 覆盖进度条的卡密验证脚本**
```sh
for i in $(seq 1 100); do printf "\r验证中... %d%%" "$i"; sleep 0.05; done
```
- **痛点**：`\r` 在 `runOne` 里被 `pendingCr=true; continue` 吞掉且无任何后续消费，HazeRoot 会把它渲染成 **100 行"验证中... N%"竖着排**，而不是原地刷新的一行。这是我在 Termux 里每天看到的正常行为，在 HazeRoot 里直接刷屏到 20 万字符上限。
- **期望**：`\r` 触发"回退到本行行首、覆盖重写当前行"，与真实终端一致。

**场景 2：脚本里 `printf "\033[2J\033[H"` 清屏后打印菜单**
- **痛点**：清屏/光标定位序列被 `feedAnsi` 丢弃，屏幕残留旧输出 + 新菜单叠在一起，菜单根本看不清，自动应答的 prompt 文本也混入残留垃圾。
- **期望**：至少支持 CSI 的 `J`（清屏）、`K`（清行）、`G`/`H`（光标定位）、`A/B/C/D`（移动），或干脆**放弃"手写 ANSI 状态机"，直接用成熟终端库**（`libtermexec` / 移植 Termux 的 `TerminalEmulator`）。

**场景 3：`ls -l /data/adb`、`df -h`、`mount` 这类表格输出**
- **痛点**：终端渲染是 `TextView` 自动 wrap，没有"列宽 cell"概念；`\t` 直接 append 进 TextView（TextView 对 tab 几乎当空格处理），列全错位。ANSI 颜色 span 在软换行后也跨行错乱。
- **期望**：等宽字体 + 字符网格渲染（`char[][]` cell），tab 按 8 列对齐，这是 Termux `TerminalRenderer` 的底线。

**场景 4：`cat` 一个含 `\u0001`（SOH 控制字符）的二进制或日志**
- **痛点**：HazeRoot 用 `\u0001 + styleChar` 做**内部 ANSI 样式标记**，脚本输出里真实的 `\u0001` 会污染 `appendStyled` 的标记解析，导致后续全部颜色错乱、甚至丢行。
- **期望**：内部标记与用户可见字符空间隔离（例如用专用 `Spannable` 结构而非在文本里塞控制字符），或对输出字节做转义。

**场景 5：UTF-8 中文 + 少量 GBK 注释的混合脚本**
- **痛点**：`hybridDecode`（1277 行）是"逐块启发式"，主路径先严格 UTF-8 试、malformed 才回退；但 UTF-8 分支的 `pendingTail = cb.remaining()` 与 hybrid 分支的 `pendingTail = bytes.length - i` **语义不一致**（一个是解码器未消费尾巴，一个是扫描器未走到位置），`carry` 混用会把已解码字节再喂一次 → 重复字/错位。这是"显示不全"的另一条独立根因。
- **期望**：单一字节流式解码器，跨 chunk 保持 `mUtf8ToFollow/mUtf8Index` 状态（Termux `TerminalEmulator.append` 模型），**绝不按 chunk 重新 `new String`**。

## 2. 脚本执行真实场景

### 2.1 ELF 执行：没有 shebang 语义、没有工作目录、没有参数

**源码证据**（`Engine.java:871-875`）：
```java
String inner = isElf
    ? "chmod +x " + q(s.getPath()) + " 2>/dev/null; " + q(s.getPath())
    : "sh " + q(s.getPath());
```

- **场景 A：跑一个 `#!/data/adb/magisk/busybox ash` 的脚本**
  - **痛点**：HazeRoot 用 `isElf`（只看前 4 字节 `\x7fELF`）二分"ELF→直接执行 / 非 ELF→`sh path`"。带 shebang 的非 ELF 脚本（busybox ash、python、perl）会被强制 `sh path` 执行，`sh` **无视 shebang 解释器**，`python 脚本` 直接语法错误。这是重度用户的高频雷区。
  - **期望**：非 ELF 时先读 shebang，有则用 shebang 解释器执行；只有无 shebang 才回退 `sh`。

- **场景 B：脚本里有 `./config`、`cat data/xxx` 这类相对路径引用**
  - **痛点**：执行命令是 `su -c "sh -c '/data/adb/HazeRoot/xxx.sh'"`，工作目录是 su 的默认目录（`/` 或 `/data/local/tmp`），**不是脚本所在目录**。相对路径全部失效。
  - **期望**：执行前 `cd "$(dirname "$path")"`，或提供"工作目录"配置项。

- **场景 C：卡密验证 ELF 需要 `./verify -k AABBCC`**
  - **痛点**：`ScriptItem` 没有"参数"字段，队列里的脚本无法带命令行参数，只能把参数写死进脚本或用 sh 包装，违背"通用执行器"定位。
  - **期望**：`ScriptItem` 增加 `args` 字段，入队时支持填参数。

### 2.2 PTY：依赖 busybox `script`，且是"半吊子 PTY"

- **源码证据**（`Engine.java:771-792, 879-884`）：
```java
boolean usePty = hasBusyboxScript();
pb = usePty
  ? new ProcessBuilder("su", "-c", "busybox script -q -c " + wrapped + " /dev/null")
  : new ProcessBuilder("su", "-c", inner);
```
- **场景：没有 busybox（toybox-only / 精简 ROM）或 busybox 无 `script`**
  - **痛点**：直接降级非 PTY，`redirectErrorStream(true)` 管道全缓冲，交互脚本的提示不实时刷出，长跑进度"攒批"（PRD 自己也承认了 A.1 第 5 条）。
  - **痛点 2**：`busybox script -c ... /dev/null` 把 typescript 写进 `/dev/null`，等于"PTY 输出先丢 /dev/null 再回读"，很多 busybox 版本 `script` 的 `-c` 支持残缺、退出码不透传，`waitFor()` 拿到的是 `script` 的返回码而非脚本返回码，只能靠 `__HR_EXIT_` 魔数兜底。
  - **期望**：自建 PTY（`PtyProcess` / 直接 `openpty` + `execve`），不依赖 busybox `script`；这才是"通用 root 执行器"该有的底子。

### 2.3 长跑守护脚本：被静默看门狗噪声 + `finalizePreset` 自杀连坐

- **场景：队列里跑一个 `while true; sleep 60; check; done` 的守护脚本**
  - **痛点 1（噪声）**：`runOne$lambda$9`（1100-1123 行）静默看门狗 idle > 12s 就 log"已 N 秒无输出"，60 秒才吐一次的守护脚本会被疯狂提示"已 60 秒无输出"，把真实输出淹没。
  - **痛点 2（自杀）**：方案（auto）模式最后一个脚本跑完且 `hadAutoInput` 时启动 `watchIdle`，30s 无输出即 `finalizePreset` → 跳目标 app + `Process.killProcess(myPid()) + System.exit(0)`（731-760 行）。**这会把 RunnerService 前台服务和挂在 app 进程下的后台守护任务一起杀掉**。一个"长跑守护脚本执行器"跑完就自杀，语义自相矛盾。
  - **期望**：看门狗只在"等输入"状态下提示，不把低频输出当卡死；`finalizePreset` 的"跳转后自杀"做成可关闭选项，且绝不连坐前台服务。

### 2.4 执行环境：最小 su 环境，缺 PATH/TERM/HOME

- **场景：脚本里 `busybox`、`magisk`、`$PREFIX/bin/xx` 找不到**
  - **痛点**：没有设置 `PATH`、`TERM`、`HOME`、`LD_LIBRARY_PATH` 环境变量，很多脚本依赖 `/data/adb/magisk/busybox`、Termux 的 `$PREFIX`，在 su 最小环境里直接 command not found。
  - **期望**：提供"环境变量 / 预置 PATH"配置，或至少继承一个合理的 root PATH。

## 3. 自动应答 / 录制 / 重放

### 3.1 录制→存方案→重放的闭环，在代码层面是断的（高危）

这是我最想吐槽的一点，也是 PRD 没覆盖到的：

- **源码证据**：
  - `Engine.java:927` 录制模式 `recordingCollect = auto ? null : new LinkedHashMap<>()`；
  - `Engine.java:230-248` `sendRaw()` 手动输入时，把 `promptKey() → value` 写进 `recordingCollect`；
  - `Engine.java:1066-1074` 收尾时：
    ```java
    collect = recordingCollect;
    if (collect != null) { Store.INSTANCE.saveScripts(appCtx, scripts); ... }
    recordingCollect = null;
    ```
  - **全工程 `setRecordedInputs(...)` 零调用**（grep 只在 `ScriptItem.java:124` 定义处出现，无任何调用点）；
  - `Engine.java:1344-1346` `resolveAnswer()` 是**死代码**，永远返回 `null`，无人调用。
- **结论**：`recordingCollect` 收集到的 prompt→value **从未被写回 `ScriptItem.recordedInputs`**。`saveScripts(scripts)` 序列化的是 `ScriptItem` 列表，而 `ScriptItem.recordedInputs` 字段在录制全程保持空。**你录了半小时回答，点保存方案，方案里是空的，重放一个答案都不会回。** "录制回答→存为方案→一键重放"这个卖点目前只存在于 UI 文案里。
- **期望**：录制收尾时把 `recordingCollect` 转成 `List<RecordedInput>` 写回 `s.setRecordedInputs(...)` 再落盘；补一个"录制后回放自检"的单测锁住这个闭环（这属于 PRD M6 该验收但没有 AC 的东西）。

### 3.2 提示匹配"精确文本 trim"的坑

- **源码证据**（`Engine.java:107-113`）：
```java
private final String promptKey() {
    String obj = trim(currentPartial);
    if (obj.length() == 0) obj = trim(lastFullLine);
    return obj;
}
```
- **场景：卡密验证脚本提示"请输入卡密(第 3/5 次): "，或带时间戳/序号/路径的提示**
  - **痛点**：`pending.get(key)` 是**精确全文匹配**。提示里只要有任何一处动态变化——序号、时间戳、路径、全角/半角、行尾空格、ANSI 剥离后残差——就匹配失败。重放时要么干等、要么漏答。
  - **期望**：匹配降级链：精确 → 去空白规范化 → 正则/包含（`contains`）→ 顺序回退（按录制顺序逐个消费）。至少要给"包含匹配"开关。

### 3.3 提示上下文抓不全 + 答案队列会错位

- **场景：多行交互菜单**（"请选择:\n[1] 验证\n[2] 退出\n> "）
  - **痛点**：`promptKey()` 只取"最后未换行的 partial"或"最后一个完整行"，抓不到完整菜单上下文，重放"选择 1 + 确认 y"这类两段式交互会错位。
  - **痛点 2（错位）**：`vals.remove(0)` 每次匹配吃掉第一个答案。脚本因网络/随机多问一次 → 答案不够干等；少问一次 → 答案错配到下一个 prompt。没有"按序消费 + 兜底"。
  - **期望**：prompt 建模为"最近 N 行上下文"，答案按**顺序队列**消费而非按 key 精确查表，配"超时未匹配则跳过/告警"。

### 3.4 早答：自动应答在提示 flush 前就写 stdin

- **源码证据**（`Engine.java:1031-1053`）：应答检查在每次 `read()` 后，`partial.length() > 0` 即尝试匹配并写 `proc.getOutputStream()`。
- **场景：`read -p "密码: " pw` 这类行内提示（末尾无 `\n`，stdio 半缓冲）**
  - **痛点**：`partial` 是"当前行累积"，提示还没打印完整（或没 flush）就可能触发应答，答案提前进入 stdin 缓冲，脚本还没进入读状态，顺序可能乱。
  - **期望**：等"提示稳定"（如 100–300ms 无新输出）后再应答，且应答后回显校验。

## 4. 队列执行

### 4.1 停止不杀子进程树（最痛）

- **源码证据**（`Engine.java:794-821`）：`abort()` 只 `currentProc.destroy()` + 关流。`currentProc` 是 `su -c "sh -c '...'"` 这个外层进程，脚本内部 `nohup`/`&`/递归 `su`/`sleep` 产生的子进程变孤儿继续跑。
- **场景：跑了个 `while true; do ...; done`，点停止，界面显示"已停止"，但后台 CPU 100%**
  - **痛点**：没有 `kill -- -PGID`、没有遍历 `/proc` 杀进程树，停止是"假停止"。
  - **期望**：启动时 `setsid` 建独立进程组，停止时 `killpg`；或至少 `pkill -P` 递归杀子进程。

### 4.2 `runningNow` 全局单例：执行中"点执行"被静默忽略

- **源码证据**（`Engine.java:550-553`）：`if (runningNow) { Log.d("被忽略"); return; }`。
- **场景：脚本 A 在跑，我想把 B 入队"排队等"**
  - **痛点**：三条路径（文件页执行 / 方案运行 / 队列运行）共享一个全局 `runningNow`，执行中再点执行被**静默丢弃**，没有"排队"语义，没有提示。
  - **期望**：区分"正在执行"与"队列排队"，执行中入队进入 PENDING 等待；或至少给明确的"已有任务在执行"反馈（现在只有部分入口 toast）。

### 4.3 失败不中断、文件缺失被标成"成功"

- **场景：队列 = [卡密验证, 注入脚本]，卡密验证 exit 1**
  - **痛点**：队列循环里 exit≠0 只是 `log(warn_nonzero)` **继续跑下一个**（1086-1095 行）。验证失败还继续跑注入脚本，可能造成设备逻辑错误。
  - **痛点 2（误导）**：`runOne` 里 `fileOk=false` 直接 `return`，`s.exitCode` 保持 null；`ScriptAdapter` 里 `exitCode==null → dot_done`。**文件不存在被显示成绿点"成功"**。
  - **期望**：失败策略可配置（失败即停 / 失败跳过 / 失败重试）；文件缺失显式置 exitCode=-1 标红。

### 4.4 退出码靠 `__HR_EXIT_` 魔数注入，脆弱

- **源码证据**（`Engine.java:876, 936, 1260-1269`）：
```java
String exitProbe = "; __hr_e=$?; printf \"\n__HR_EXIT_%s__\" \"$__hr_e\"";
```
- **场景：脚本自己输出里恰好包含 `__HR_EXIT_123__`（日志、脱敏串）**
  - **痛点**：正则 `__HR_EXIT_(\d+)__` 会误匹配脚本输出，把 exitCode 覆盖成错误值；PTY 路径下 `busybox script` 的 `waitFor()` 退出码本就不透传，全靠这个魔数，双倍脆弱。
  - **期望**：用单独的退出码通道（临时文件/pipe FD），不用注入到 stdout 的魔数。

### 4.5 长队列每个脚本后都落盘，浪费 + 竞争

- **源码证据**（`Engine.java:639-645`）：每跑完一个脚本 `store.saveScripts`（`apply()` 异步写 SharedPreferences）。
- **痛点**：长队列频繁写全量 JSON，性能浪费，且与录制收尾的 `saveScripts` 并发竞争。
- **期望**：队列结束后统一落盘一次。

## 5. 与 MT / Termux 的真实差距（按"每天都要用"优先级）

1. **不是交互式终端，废一半交互脚本**（最高）
   没有 termios/raw mode、没有 Ctrl-C/Ctrl-D/Ctrl-Z、没有 Tab 补全、没有命令历史。手动输入框一次发一整行，**发不了 Ctrl-C 去中断一个正在等输入的命令**。`adb shell`、`sqlite3`、需要密码的 `su`、vim/nano 全部无法用。
2. **辅助键（Esc/Tab/Ctrl/方向键）是空谈**
   文档 A.2.6 画的辅助键行**根本没实现**。`QueueFragment` 只有一个 EditText + 发送。menuconfig、交互菜单、选择框大量依赖方向键，没有辅助键 = 交互脚本废掉另一半。
3. **执行路径断裂、摩擦大**
   MT 是"双窗就地操作"，HazeRoot 是文件页→确认框→切队列页的三段跳；且文件页"执行"要弹确认框，每天跑脚本的人会觉得这个确认框是纯摩擦。
4. **没有输出保存/导出**
   跑完没"复制全部/导出文件/分享日志"。卡密失败要看日志发群里，只能长按 TextView 复制，而 20 万字符上限 + 截断丢最旧内容，日志根本复制不全。
5. **编辑器不能"就地运行"**
   `EditorActivity` 只有编辑+保存，没有"保存并运行"。Termux 用户习惯 `nano → 跑`，HazeRoot 要 编辑→返回→队列→执行 四步。
6. **没有环境/profile**
   Termux 有 `$PREFIX`、可配环境变量，HazeRoot 是 su 最小环境，无法为脚本配置 PATH/工作目录。

## 6. 重度用户视角的 P0/P1 需求排序

> 注：以下**替换/补充** PRD 的 FR 排序，因为 PRD 把大量精力放在"文件页手势/换肤/MT 对齐"上，而重度用户每天的核心痛点是**终端 + 执行语义 + 录制闭环**。

### P0（不做就没法日常用）

| # | 需求 | 对应本报告问题 | 为什么是 P0 |
|---|---|---|---|
| P0-1 | 终端内核重建：字节流解码器 + 字符网格渲染 + 完整 CSI（光标/清屏/`\r` 覆盖/`\t` 对齐） | §1.1 / §1.2 | 显示不全、进度条坏、表格错位是"看都看不清"级别的 |
| P0-2 | 录制闭环修复：`recordingCollect` 回写 `ScriptItem.recordedInputs`，删死代码 `resolveAnswer` | §3.1 | 核心卖点"一键重放"目前是空的，属于功能缺失 |
| P0-3 | 停止杀进程树 + 退出码独立通道（去 `__HR_EXIT_` 魔数） | §4.1 / §4.4 | "停止不干净"会直接烧电池/烧 CPU，是安全级问题 |
| P0-4 | ELF/shebang 语义 + 工作目录 + 参数传递 | §2.1 | 三分之一的真实脚本跑不对，执行器基本功 |
| P0-5 | 自建 PTY（不依赖 busybox `script`）+ raw mode + Ctrl-C/D 控制字符 | §2.2 / §5.1 | 交互脚本是 root 玩家的大头 |

### P1（明显提升体验，但不阻断日常）

| # | 需求 | 对应问题 |
|---|---|---|
| P1-1 | 提示匹配降级链（精确→规范化→包含→正则→顺序回退）+ 多行上下文 | §3.2 / §3.3 |
| P1-2 | 队列状态机：排队语义、失败策略（停/跳/重试）、文件缺失标红 | §4.2 / §4.3 |
| P1-3 | 输出保存/导出/分享 + 日志滚动不丢最旧 | §5.4 |
| P1-4 | 辅助键行（Esc/Tab/Ctrl/方向键）落地 | §5.2 |
| P1-5 | 执行路径联动（文件页执行自动切终端、去掉多余确认框） | §5.3 |
| P1-6 | 环境变量/PATH/工作目录 profile | §2.4 / §5.6 |

### P2（锦上添花，PRD 已覆盖的不重复）

- 文件页手势状态机、长文件名、MT 范式对齐、UI 换肤 —— 这些**该做**，但优先级应让位于上面 P0/P1。一个连"进度条都显示不对、录制重放是空的"的终端，先对齐 MT 的手势是**本末倒置**。

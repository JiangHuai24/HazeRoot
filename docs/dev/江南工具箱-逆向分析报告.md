## 二、加固判定：自研/乐固系壳（`zz` 命名空间）

**证据链：**

1. `AndroidManifest.xml`：`android:name="zz.S"`（Application），且 `compileSdkVersion=34`。
2. `classes.dex` 仅 **52,428 字节**（正常 App 应为数 MB），说明真实代码被抽离加密。
3. `assets/prot/` 下 40+ 个无扩展名加密载荷：
   - `boot.bin`（318B，加密 JSON 配置，含 mode/ver/ktag/sbm/sms/wbs 等密钥字段）
   - `c.bin`（1589B，加密主配置，解密后含 guard/dex/real_app 等字段）
   - `d0.bin ~ d8.bin`（加密 DEX，`d0.bin` 5.6MB 为最大主 dex）
   - `m0.bin ~ m8.bin`（加密资源/媒体）
   - `r0.bin ~ r15.bin`（加密资源）
   - `a.bin`(44B) / `sa.bin`(16B) / `sb.bin`(16B) / `wb.bin`(60B)（密钥素材）
   - `g.bin`(340B，加密 guard 配置）
4. `lib/arm64-v8a/libzzcore.so`（47KB）+ `libjn_pty.so`（149KB，PTY 终端 native 库）。
5. 壳的 `zz/L.smali` 逆向还原出完整加载流程（见下）。

## 三、壳加载流程（zz/L 逆向还原）

```
attachBaseContext → zz/L.boot()
  ├─ hardDbgGuard（反调试，zz/G）
  ├─ loadBoot()：读 sb.bin + boot.bin
  │    密钥派生：SHA256("zz.boot.v2|" + packageName + "|" + hex(sb.bin))
  │    boot.bin[0..12]=nonce，[12..]=密文，AES 解密得 JSON
  ├─ N.load()：加载 libzzcore.so
  ├─ N.guard() + G.nativeGuard()：native 层守护
  ├─ N.init(pkg, ver, a.bin, sa.bin, shareB)：native 初始化，返回句柄
  ├─ N.dec(handle, "c.bin", ...)：解密主配置 JSON
  ├─ R.prepare() + R.attachAssets()：解密资源
  ├─ install()：解密并加载 DEX
  │     ├─ installInMemory：N.decDex → InMemoryDexClassLoader（内存加载）
  │     └─ installOnDisk：N.decDex → 写 codeCache/zzdx/classes.dex → DexClassLoader
  │     ├─ 混淆字符串解码（zz/U.s() 逐字节异或）：
  │     │    "dalvik.system.InMemoryDexClassLoader"（shift=0x47）
  │     │    "dalvik.system.DexClassLoader"（shift=0x2b）
  │     │    "classes.dex"（shift=0x59）/"zzdx"（shift=0x21）
  │     └─ inject()：把新 ClassLoader 的 dexElements 注入宿主 ClassLoader
  ├─ 从 c.bin 读 "real_app" → Class.forName → attachReal → swapActivityThread
  └─ start()：替换 Application，watchActivities
```

## 四、native 层符号（libzzcore.so 导出）

| 导出符号 | 作用 |
|---|---|
| `Java_zz_N_init` | 初始化密钥上下文 |
| `Java_zz_N_initLocal` / `initLocal6` | 本地模式密钥派生（v4/v6 协议） |
| `Java_zz_N_dec` | 解密普通载荷（c.bin/g.bin） |
| `Java_zz_N_decDex` | 解密 DEX 载荷 |
| `Java_zz_N_selftest` / `guard` | 自检/守护 |
| `Java_zz_N_maskKey` / `wipe` / `sha256` | 密钥掩码/擦除/哈希 |

## 五、libjn_pty.so（PTY 终端能力）

导出符号对应 `com.jiangan.toolbox.core.PtyProcessNative`：
- `create`（创建 PTY 进程）/ `read` / `write` / `resize` / `close` / `pid` / `setEcho` / `waitFor`

**功能推断**：江南工具箱内置了 **PTY 伪终端执行能力**（原生 PTY + 终端尺寸调整 + echo 控制），用于运行 shell 命令并显示真实终端效果。这与 HazeRoot 的 `busybox script` PTY 方案是同一技术目的，但江南用的是**原生 JNI PTY**（更稳、更实时），这是值得 HazeRoot 借鉴的技术点。

### 6.2 底部导航栏（精确像素测量，复刻关键数据）

从 6 张截图（1080×2400）像素分析得出：

| 项 | 测量值 |
|---|---|
| 导航栏高度 | ~46dp（截图 y≈2280–2400） |
| 导航栏样式 | **单色极简 + 选中高亮** |
| 选中态 | 图标+文字亮白（lum≈209，接近白） |
| 未选中态 | 中性灰（lum≈106–130，即 `label_tertiary` 量级） |
| 左侧第一个 tab 图标 x 起始 | ~24dp |
| 布局 | 图标+文字横向排布，无彩色胶囊、无渐变 |

**复刻要点**：江南工具箱导航是「选中=亮、未选中=灰」的单色极简导航，**没有 HazeRoot 现在那种 `accent_tint14` 彩色胶囊底**。这恰好印证了 UI 建议书「去 AI 味」的方向。

## 七、对 HazeRoot 的可借鉴点

1. **原生 PTY（libjn_pty.so）替代 `busybox script`**：解决"PTY 输出攒批不实时"的历史问题（HazeRoot 交接文档 7.3）。
2. **单色极简底部导航**：选中=亮白、未选中=灰，去掉彩色胶囊底。
3. **悬浮窗监控服务**（FPS/温度）：HazeRoot 可作为后续方向（执行进度悬浮球）。

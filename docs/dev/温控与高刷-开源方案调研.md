# 温控管理 & 强制高刷 —— 开源实现调研（供 HazeRoot 借鉴）

> 调研时间：2026-11-02
> 目标：为 HazeRoot（Java 17 + AppCompat，minSdk 26 / targetSdk 34，root 脚本执行器）新增
> 「CPU/电池温控管理」与「强制高刷新率」两个功能，找**维护活跃、许可证明确**的开源实现做设计借鉴。
> 方法：GitHub 仓库搜索 + 逐仓库拉源码（`git clone --depth 1`）读实现 + AOSP 源码交叉验证 API 语义。
> 所有结论均来自实际读过的文件，文中给出的路径/命令都可在对应仓库或 AOSP 里逐字核对。

## 0. 一句话结论（先看这个）

| 功能 | 推荐主借鉴 | 许可证 | 理由 |
|---|---|---|---|
| **温控** | `MaheshSharan/FrameX-Android`（读数/状态解析） + `helloklf/vtools`（小米配置覆写思路） + `Grarak/KernelAdiutor`（节点清单，仅抄"节点名"这一层事实） | MIT / GPL-3.0 / GPL-3.0 | FrameX 的 `dumpsys thermalservice` 解析器是**唯一 MIT、可直接移植**的高质量实现；vtools/MiThermalTuner 的 AES 配置文件路线是小米系"真温控"的唯一可行路线，但**只能学思路、不能抄代码**（GPL） |

## 2. 温控实现思路对比

Android 温控有**四层**，各项目分别在不同层动手。理解这个分层是看懂所有实现的前提：

```
① 内核温区      /sys/class/thermal/thermal_zone*/{type,temp,policy,mode}
② 散热设备      /sys/class/thermal/cooling_device*/{type,cur_state,max_state}
③ 厂商/HAL 守护  mi_thermald / thermal-engine / thermald / MTK thermal / android.hardware.thermal@2.0-service
④ 框架层        ThermalService（cmd thermalservice）+ PowerManager 热状态
```

### 2.1 各项目落点对比表

| 项目 | ① 温区读数 | ② cooling_device | ③ 厂商守护 | ④ 框架热状态 | 是否改配置 |
|---|---|---|---|---|---|
| FrameX-Android | 兜底读 | 读 | 不碰 | **解析 `dumpsys thermalservice`** | 否（只读） |
| vtools（Scene） | 读 | 读 | 停/改 msm_thermal、小米 board_sensor_temp | 否 | **是**（小米 AES 配置 + Magisk 覆盖 /vendor/etc） |
| MiThermalTuner | 读 7 路具名传感器 | 读 53 个 | **AES 解密改写 + `ctl.restart mi_thermald`** | 读 `thermal_message/temp_state` | **是**（小米） |
| KernelAdiutor | `thermal_zone0/temp` | 否 | 启停 `thermald` 服务 | 否 | 否 |
| SmartPack | 同 KA | 否 | 改 msm_thermal 节点 | 否 | 否 |
| BS-THERMAL | 全局禁用 | 否 | 停所有 thermal 服务、freeze 进程 | `cmd thermalservice override-status 0` | 否（全拆） |

### 2.2 具体节点与命令（可直接照抄的事实层）

#### A. 温度读数

```bash
# 通用：内核温区（值单位 millidegree，需 /1000）
for z in /sys/class/thermal/thermal_zone*; do
  echo "$(cat $z/type) $(cat $z/temp)"
done

# 电池（单位 0.1℃）
cat /sys/class/power_supply/battery/temp

# 小米专有具名传感器（MiThermalTuner monitor.sh 实证）
/sys/class/thermal/thermal_zone*/type  →  quiet_therm / cpu_therm / battery /
   charger_therm0 / wifi_therm / modem1_pa0 / modem1_pa1 / flash_therm
```

> KernelAdiutor 的 `Temperature.java` 还有一个很实用的**偏移量自适应**技巧：不同机型 `temp` 文件可能是 2 位数（37）或 5 位数（37000），它用
> `if (offset != 1 && read().length() == 2) offset = 1;` 自动纠偏——比硬编码 `/1000` 稳。

#### B. 散热设备档位（真正"当前被限了多少"的证据）

```bash
for c in /sys/class/thermal/cooling_device*; do
  echo "$(cat $c/type) $(cat $c/cur_state)/$(cat $c/max_state)"
done
```

`cur_state != 0` 就代表这个散热设备正在介入。MiThermalTuner 用这条规则列出"当前介入中的散热设备"，
FrameX 用同一规则判断 `isCpuThrottling`（`CoolingDevice{mValue>0}` 且 name 含 `cpufreq/cpu-cooling/thermal-cpufreq`）。

#### C. 框架层热状态（root 下最"正统"的开关）

```bash
dumpsys thermalservice            # 输出 "Thermal Status: N"、"Current temperatures from HAL:"、"Current cooling devices from HAL:"
cmd thermalservice override-status 0    # 强制热状态 = NONE（0..6，6 是 SHUTDOWN）
cmd thermalservice reset                # 取消覆盖
cmd power set-fixed-performance-mode-enabled true
cmd power set-adaptive-power-saver-enabled false
```

> **AOSP 交叉验证**（`services/core/java/com/android/server/power/ThermalManagerService.java`）：
> `publishBinderService(Context.THERMAL_SERVICE, ...)`，`Context.THERMAL_SERVICE = "thermalservice"`；
> shell 子命令为 `inject-temperature` / `override-status` / `reset` / `headroom`。
> 所以正确写法是 **`cmd thermalservice override-status 0`**；`init-java/refresh_thermal_lock` 里写的 `cmd thermal override-status 0`
> 少了 `service` 后缀，属于**该仓库的 bug**（见 §4.3），不要照抄。

#### D. 高通 msm_thermal 驱动节点（老机型 / 自定义内核）

KernelAdiutor `MSMThermal.java` 与 SmartPack `MSMThermalSimple.java` 给出的完整清单：

```
/sys/module/msm_thermal/parameters/enabled                 (Y/N)
/sys/module/msm_thermal/parameters/intelli_enabled         (Y/N)
/sys/module/msm_thermal/parameters/limit_temp_degC
/sys/module/msm_thermal/parameters/core_limit_temp_degC
/sys/module/msm_thermal/parameters/temp_hysteresis_degC
/sys/module/msm_thermal/parameters/poll_ms
/sys/module/msm_thermal/parameters/freq_step
/sys/module/msm_thermal/core_control/enabled               (1/0)
/sys/module/msm_thermal/vdd_restriction/enabled            (1/0)
/sys/kernel/msm_thermal/enabled
/sys/kernel/msm_thermal/conf/{allowed_low_low,allowed_low_high,allowed_low_freq,
                              allowed_mid_*,allowed_max_*,check_interval_ms,shutdown_temp}
/sys/class/misc/tempcontrol/templimit                      (毫度，offset=1000)
```

vtools 的 `ThermalControlUtils.java` 只挑了 3 个最通用的（core_control / vdd_restriction / parameters.enabled），
写前先 `chmod 0664`——这一步很关键，很多机型默认 0444。

#### E. 小米专有：`thermal_message` 与 `mi_thermald` 配置

```bash
# 系统温控状态机（0/1/2…，直接影响通知、省电、相机可用性）
/sys/class/thermal/thermal_message/temp_state
# 主板传感器温度（vtools 用它做"伪装"绕过小米游戏温控）
/sys/class/thermal/thermal_message/board_sensor_temp
# 小米 GPU 上限参数
/sys/module/migt/parameters/glk_maxfreq

# 配置覆写目录（mi_thermald 优先读这里，回退 /vendor/etc）
/data/vendor/thermal/config/thermal-*.conf
# 运行时解密出的当前生效配置（用来验证"真的生效了"）
/data/vendor/thermal/decrypt.txt
# 重启守护使其重新加载
setprop ctl.restart mi_thermald
```

**配置文件是 AES-128-CBC 加密的**（vtools `MiuiThermalAESUtil.java` + MiThermalTuner `docs/thermal-config-format.md` 双向印证）：

| 项 | 值 |
|---|---|
| 算法 | AES-128-CBC + PKCS#5/PKCS#7 padding |
| Key | ASCII `thermalopenssl.h`（16 字节） |
| IV | 与 Key 相同 |
| 判据 | 文件长度为 16 的整数倍 → 加密；否则明文（如 `thermal-chg-only.conf`） |
| 密钥来源 | 硬编码在 `/vendor/bin/mi_thermald` 的 `.rodata` |

配置语法（INI 风格，`[节名]` + `键<空白>值`）：

```ini
[BAT_SOC]
algo_type   simulated
path        /sys/class/power_supply/battery/capacity
polling     10000

[VIRTUAL-SENSOR]
algo_type   virtual
sensors     quiet_therm  modem1_pa0  modem1_pa1  charger_therm0  wifi_therm  cpu_therm  battery
weight      -155         424         -8          86              -3          237        288
weight_sum  1000
compensation 2699

[MONITOR-SS-CPU4]
algo_type   ss
sensor      VIRTUAL-SENSOR
device      cpu4
polling     2000
trig        39000  40200  41000  45000  47000
clr         37000  39000  40200  42000  45000
target      1651200 1516800 1228800 940800 691200
```

`algo_type`：`simulated`（直读 sysfs）/ `virtual`（多传感器加权合成）/ `ss`（阶梯降频，越线切 target）/ `monitor`（越线切 target，可用于电量、背光、状态码）。
`device` 取值：`cpu0/cpu4/cpu7`、`gpu`、`battery`（充电限流档）、`backlight-clone`、`modem_ul/dl`、`temp_state`、`hotplug_cpu6+hotplug_cpu7`。

#### F. CPU 频率限制（"温控之外"的直控层）

```bash
# 集群上限（policyN，N 对应 cluster，不是核号）
cat /sys/devices/system/cpu/cpufreq/policy4/cpuinfo_max_freq
echo 1516800 > /sys/devices/system/cpu/cpufreq/policy4/scaling_max_freq

# GPU（高通 kgsl）
cat /sys/class/kgsl/kgsl-3d0/devfreq/available_frequencies
echo 315000000 > /sys/class/kgsl/kgsl-3d0/devfreq/max_freq
```

MiThermalTuner 的 `mt cap cpu 4 1516800` / `mt cap gpu 315000000` 就是这两条；`mt cap cpu 4 off` 则回读 `cpuinfo_max_freq` 写回 `scaling_max_freq` 恢复。

## 3. 高刷实现思路对比

### 3.1 五种手段的能力矩阵

| 手段 | 具体命令 / API | 需 root | 生效范围 | 兼容性 | 代表项目 |
|---|---|---|---|---|---|
| ① Settings 系统键（AOSP 正统） | `settings put system peak_refresh_rate 120` / `min_refresh_rate 120` | 否（adb/root 均可） | 全局、跨应用 | 原生/Pixel 好；**MIUI/ColorOS 常被自家逻辑覆盖** | dfps、refresh_thermal_lock |
| ② 厂商私有键 | 小米 `settings put secure miui_refresh_rate 120` / `user_refresh_rate`；三星 `secure refresh_rate_mode`；vivo `secure active` | 否 | 全局 | 各厂差异极大，需分支 | Adaptive-Hz、akihz、RefreshRateSwitcher |
| ③ SurfaceFlinger 事务码 | `service call SurfaceFlinger 1035 i32 <index>`；强制刷新序 `1036 1 → 1035 -1 → 1036 0 → 1035 <idx>` | 是 | 直接切物理显示模式 | 强，但 **index ≠ modeId**，必须解析 | dfps、CuRefreshRateTuner、RefreshRateSwitcher |
| ④ `cmd display`（Android 14+ 最稳） | `cmd display set-user-preferred-display-mode W H FPS DISPLAY_ID` | 是（shell 权限） | 全局、按物理分辨率+fps 匹配 | 需要 API 34+ | RefreshRateSwitcher（实测"最稳"） |
| ⑤ 悬浮窗 `preferredDisplayModeId` | `WindowManager.LayoutParams.preferredDisplayModeId = modeId` + `preferredRefreshRate` | **否** | 仅该窗口存活期间 | 免 root 唯一解；会常驻"上层显示"提示 | RefreshRateSwitcher `OverlayModeSwitch.java` |

### 3.2 关键源码逐条对照

#### A. dfps（Apache-2.0，`source/utils/misc_android.cpp`）

```cpp
void SysPeakRefreshRate(const std::string &hz, bool force) {
    CallSettingsPut("system", "peak_refresh_rate", hz.c_str());
    CallSettingsPut("system", "min_refresh_rate",  hz.c_str());
    CallSettingsPut("system", "miui_refresh_rate",  hz.c_str());   // 小米
    CallSettingsPut("secure", "miui_refresh_rate",  hz.c_str());   // 小米
}

void SysSurfaceflingerBackdoor(const std::string &idx, bool force) {
    SyncCallSurfaceflingerBackdoor("1035", idx.c_str());           // setActiveConfig
    if (force) {                                                    // Android 11+ 强制生效技巧
        SyncCallSurfaceflingerBackdoor("1036", "1");                // acquire frame-rate flexibility token
        SyncCallSurfaceflingerBackdoor("1035", "-1");
        SyncCallSurfaceflingerBackdoor("1036", "0");                // release
        SyncCallSurfaceflingerBackdoor("1035", idx.c_str());
    }
}
```

`1036` 那套"拿 token → 清空 → 释放 → 再设"是**绕过系统 director 覆盖**的关键黑魔法，dfps 是这套写法的源头。
它还明确记录了 SF index 与刷新率的对应关系**因机而异**：

```
0:120 / 1:90 / 2:60
0:60  / 1:90
0:30 / 1:50 / 2:60 / 3:90 / 4:120 / 5:144
0:1080p60 / 1:1440p120 / 2:1440p60 / 3:1080p120
```

→ **不能假设顺序**，必须自己枚举验证。

#### B. CuRefreshRateTuner（BSD-3-Clause，`src/modules/refresh_rate_tuner.cpp`）

它解决了"index 从哪来"的问题——解析 `dumpsys display`：

```cpp
// 新格式：DisplayMode{id=0,width=1080,height=2460,...,refreshRate=144.00002,...}
// 老格式：DisplayModeRecord{mMode={id=1,width=1080,height=1920,fps=60.000004}}
// 注意：老格式里 id 要 -1 才是 SF index，新格式 id 直接可用
int id = ...; if (oldFormat) id -= 1;
displayModeMap_[refreshRate][width] = id;
```

复位逻辑（换机/亮屏时很重要）：

```cpp
if (api_level >= 31 && isFlymeOS()) run("service call SurfaceFlinger 1037");
if (api_level >= 30)                run("service call SurfaceFlinger 1036 i32 0");
if (api_level >= 29)                run("service call SurfaceFlinger 1035 i32 -1");
```

#### C. RefreshRateSwitcher（MIT，`ModeUtil.java`）—— 最完整的现代写法

```java
public static boolean applyMode(Context ctx, int modeId) {
    // 0) 免 root：1x1 透明悬浮窗 + preferredDisplayModeId + preferredRefreshRate
    OverlayModeSwitch.request(ctx, modeId, wantFps);

    if (hasRoot()) OverlayModeSwitch.release();   // 有 root 就撤掉悬浮窗，避免"上层显示"提示
    if (!hasRoot()) return ...;

    // 1) Android 14+ 首选：cmd display（按物理分辨率+fps 匹配，最稳）
    String cmd = "cmd display set-user-preferred-display-mode "
               + m.getPhysicalWidth() + " " + m.getPhysicalHeight() + " "
               + Math.round(m.getRefreshRate()) + " " + displayId;
    ok = exec(cmd);

    // 1.5) HyperOS：只切 SF 会被 LTPO 自适应逻辑吃掉，必须同时钉住上限
    setRefreshRateCap(fps);

    // 2) 兜底：SF 事务码 1035，索引优先从 dumpsys 解析，取不到才退 modeId-1
    exec("service call SurfaceFlinger 1035 i32 " + sfIndex);
}

public static void setRefreshRateCap(int fps) {
    exec("settings put secure miui_refresh_rate " + fps
       + "; settings put secure user_refresh_rate " + fps
       + "; settings put system plugin_refresh_rate " + fps);
}
```

两个非常有价值的**实战坑位注释**（原文）：

- `sfIndexFor()`：`dumpsys display | grep -m1 supportedModes` 里解析 `id=(\d+)[^}]*?sfModeId=(\d+)`；"小米 17 Pro 是 1→0、3→5、4→6，所以不能一律减一"。
- `ScreenInfo.java`：LTPO 判据只能用 `DisplayDeviceInfo` 的 `hasArrSupport`，**不能用 `alternativeRefreshRates`**——普通固定刷新率面板也会列出 alternatives。
- 面板实际刷新率读取路径：`/sys/devices/virtual/mi_display/disp_feature/disp-DSI-0/dynamic_fps`（小米），直读被 SELinux 拦，需 root `cat`。

悬浮窗那条路（免 root）的核心就 4 行：

```java
WindowManager.LayoutParams lp = new WindowManager.LayoutParams(
        1, 1, TYPE_APPLICATION_OVERLAY,
        FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCHABLE | FLAG_NOT_TOUCH_MODAL,
        PixelFormat.TRANSLUCENT);
lp.alpha = 0.01f;
lp.preferredDisplayModeId = modeId;     // 让 DisplayModeDirector 收下这个 "app request"
if (fps > 0) lp.preferredRefreshRate = fps;   // 把 app request 区间钉成 [fps, fps]，抬高 LTPO 下限
```

#### D. Adaptive-Hz（MIT，`XiaomiStrategy.kt` + `RefreshRateController.kt`）

它把"小米系到底写哪个 key"做成了版本分支，这个表**非常值钱**：

| HyperOS 版本 | namespace/key | 特殊值 |
|---|---|---|
| HyperOS 1 | `secure/user_refresh_rate` | 强制最低用 `0`、强制最高用 `1`（不是 Hz！） |
| HyperOS 2 | `secure/miui_refresh_rate` | 直接用物理 Hz |
| HyperOS 3 | `secure/miui_refresh_rate`（默认） | 直接用物理 Hz；候选键按"当前值是否等于实际活动模式"排序 |
| 未知/MIUI | `secure/miui_refresh_rate` | 物理 Hz |

版本探测：`ro.mi.os.version.name` → `ro.mi.os.version.incremental` → `ro.build.version.incremental`（通过 `android.os.SystemProperties` 反射读），再用正则 `(?:HYPER\s*OS|HYPEROS)\s*[_\- ]?(\d+)` 提取主版本。
**写入后一定回读校验**，把结果分成 `AppliedAndVerified / WrittenButUnverified / VerificationMismatch / WriteRejected` 四态——这个 FSM 值得直接搬。

| 三星 | `secure refresh_rate_mode`、`system peak/min_refresh_rate`、`secure user_refresh_rate` | mode 值 0/1/2 |

| ASUS/ROG、Motorola、Sony | `system peak/min_refresh_rate`、`global user_preferred_refresh_rate` | |
| Pixel | `system peak/min_refresh_rate`、`secure smooth_display_entry_point` | |

#### F. AOSP 交叉验证（确认 API 语义，避免抄错）

- `Settings.System.PEAK_REFRESH_RATE` / `MIN_REFRESH_RATE` 由 `DisplayModeDirector` 以 **`getFloatForUser`（浮点！）** 读取，投票优先级 `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE`；`Settings.Secure.MATCH_CONTENT_FRAME_RATE` 控制切换策略。→ 写 `120` 可以，写 `120.0` 更规范。
- `cmd display set-user-preferred-display-mode WIDTH HEIGHT REFRESH-RATE [DISPLAY_ID]` 确实存在于 `DisplayManagerShellCommand`；对应的 Java API 是 `DisplayManager.setUserPreferredDisplayMode()`，注解要求 `MODIFY_USER_PREFERRED_DISPLAY_MODE` 权限（普通 App 拿不到，root/shell 才有）。
- `Surface.setFrameRate(float, int compatibility, int changeStrategy)` 存在，`FRAME_RATE_COMPATIBILITY_FIXED_SOURCE`、`CHANGE_FRAME_RATE_ONLY_IF_SEAMLESS` 可用；但它是**逐 Surface 的**，对"整个系统锁 120Hz"无效，只适合 App 自己声明内容帧率。

## 4. 已知问题与坑

### 4.1 权限与前提

| 需求 | 说明 |
|---|---|
| root | 改 sysfs、`service call`、`cmd display`、`setprop ctl.restart` 全都要 root（HazeRoot 已有 `SuGateway`，天然满足） |
| `WRITE_SECURE_SETTINGS` | 用 Java `Settings.Secure.putInt` 写 `miui_refresh_rate` 需要它；**用 `su -c settings put ...` 就绕过**——HazeRoot 应统一走 shell，不要申请这个权限 |
| SELinux | 直读 `/sys/.../dynamic_fps`、`thermal_zone*/temp` 常被拦，必须 `su -c cat`。不要用 `FileReader` 直读 |
| mount | 改 `/vendor/etc/thermal-*.conf` 需要重新挂载（vtools 里那一堆 `mount -o rw,remount`）；**推荐改用 `/data/vendor/thermal/config/` 覆写目录**，无需挂载、卸载即恢复 |

### 4.2 厂商差异（按严重程度排序）

1. **MIUI/HyperOS 会覆盖 AOSP 键**：只写 `peak_refresh_rate` 在小米上经常无效，必须补 `secure miui_refresh_rate` + `user_refresh_rate`；HyperOS 1 还要用 `0/1` 特殊值。
2. **LTPO 屏"看起来锁了其实没锁"**：framework 报 120，实际 render 只有 10–60。判据只能用 `hasArrSupport` + `renderFrameRate`，且必须用悬浮窗 `preferredRefreshRate` 把 app request 区间钉成 `[fps,fps]`。
3. **SF 事务码的 index 不是 modeId**：HyperOS/部分小米机型存在 `1→0`、`3→5` 这种映射，一律 `modeId-1` 会切错屏或切到 60Hz。
4. **ColorOS/realme/OPPO**：`peak_refresh_rate` 生效但"智能切换"会拉回 60；需同时写 `secure user_refresh_rate`，并在设置页提示用户关掉"智能刷新率"。
5. **vivo/iQOO**：走 `secure active`，且部分机型只认 `settings put system peak_refresh_rate` 的整数。
6. **通话场景温控极激进**：小米 `thermal-phone.conf` 27℃ 就开始降频（MiThermalTuner 实测数据），"解除温控"后通话/充电发热会明显上升。
7. **`mi_thermald` 重启窗口 1–2 秒策略失效**：属正常现象，但要提示用户不要在重启瞬间跑压力测试。
8. **MTK 与高通节点完全不同**：MTK 是 `/proc/ppm/policy_status`、`/proc/gpufreq/*`、`/proc/driver/thermal/tz*`；高通是 `/sys/module/msm_thermal/*`、`/sys/class/kgsl/*`。必须按 `ro.board.platform` 分支。

### 4.3 明确记录到的"别人的 bug"（照抄就踩）

| 项目 | 问题 | 正确做法 |
|---|---|---|
| init-java/refresh_thermal_lock | `cmd thermal override-status 0` —— 服务名少了 `service` | `cmd thermalservice override-status 0`（AOSP `Context.THERMAL_SERVICE = "thermalservice"`） |
| 同上 | **无 LICENSE 文件** | 视为"保留所有权利"，只读思路不抄代码 |
| Januur/UniversalThermalFix | 直接 `chmod 644 /vendor/etc/thermal-engine.conf` + 全核改 `conservative` | 改 `/data/vendor/thermal/config/`；别动 governor |
| BS-THERMAL | `chmod 000` 整个 `/sys/devices/virtual/thermal`、`kill -STOP` 温控进程、`resetprop` 改 `ro.*thermal` | 过于激进，会导致热失控/无法降频/相机被禁；**只在"临时压测"场景提供，且必须一键恢复** |
| KernelAdiutor / SmartPack | 全部 `archived`（分别 2019、2023） | 只借节点清单，不要指望长期维护 |
| dfps | 只支持 Android 10–13 | Android 14+ 需补 `cmd display` 路径 |

### 4.4 检测 / 风险（作者已在功能设计里要求评估）

- **游戏反作弊**：主流竞技手游会检测 `settings` 异常值、`SurfaceFlinger` 事务调用、`su` 进程。锁定刷新率本身风险低（系统设置级），但**频繁 `service call SurfaceFlinger` 可能被行为特征捕获**；`cmd power set-fixed-performance-mode-enabled true` 属于"高性能模式"级别信号，风险更高。
- **账号风险**：竞速/帧率敏感类游戏（和平精英、王者荣耀）把"非官方帧率"当外挂特征的概率存在但不高；**不建议默认开启**，做成分应用开关 + 明确提示。
- **保修/硬件**：解除温控长期高温会加速电池老化，小米系机型在 `thermal-phone` 场景下尤为明显。UI 上必须有"恢复原厂"一键按钮。
- **OTA 后失效**：小米 OTA 后 `thermal-*.conf` 结构可能变化，MiThermalTuner 明确建议升级后跑一次 `mt decrypt` 刷新缓存。

## 5. 给 HazeRoot 的推荐方案

### 5.1 结论：分别借鉴谁

| 模块 | 借鉴对象 | 借什么 | 不借什么 |
|---|---|---|---|
| 温控-读数与状态 | **FrameX-Android（MIT）** | `dumpsys thermalservice` 解析策略（先 `Current temperatures from HAL:` 段、按 `mType` 优先再按 `mName` 关键词、CPU 候选分级 PACKAGE>CLUSTER>CORE>TSENS>HOTSPOT、cooling_device 判 `isCpuThrottling`）—— **纯逻辑，可 1:1 翻成 Java** | Compose UI、Shizuku 集成 |
| 温控-节点清单 | KernelAdiutor / SmartPack（GPL） | **只借"节点路径字符串"这一层事实**（路径不是表达，不受版权保护） | 任何 Java 实现代码 |
| 温控-小米配置 | vtools / MiThermalTuner（GPL） | 设计：① 只写 `/data/vendor/thermal/config/`，不碰 `/vendor/etc`；② 写完校验 `decrypt.txt` 字节比对；③ `setprop ctl.restart mi_thermald` 生效 | 任何代码；AES 实现自己按公开的 "AES-128-CBC + key=iv=thermalopenssl.h" 用 JCE 写（这属于算法事实，且我们可以选择**只做"整份配置替换"不做"逐键编辑"**，减少工作量） |
| 温控-框架层开关 | AOSP 文档 + refresh_thermal_lock 的**思路** | `cmd thermalservice override-status N` / `reset`、`cmd power set-fixed-performance-mode-enabled` | 该仓库代码（无许可证） |
| 高刷-命令层 | **RefreshRateSwitcher（MIT）** | 多路径回退顺序：`cmd display` → 厂商 settings → SF 1035；`dumpsys display` 解析 `sfModeId`；HyperOS 三个 key 一起钉 | Compose UI、悬浮窗那套（HazeRoot 有 root，不需要免 root 路径） |
| 高刷-底层语义 | dfps（Apache-2.0） | `1036` token 强制刷新序列；SF index ↔ 刷新率映射的不确定性认知 | C++ 代码 |
| 高刷-厂商表 | akihz（MIT）/ Adaptive-Hz（MIT） | 厂商 key 对照表结构 + HyperOS 版本分支 + 写入四态校验 FSM | 其 Compose/DI 架构 |

### 5.2 为什么不选其他的

- **不选 BS-THERMAL / UniversalThermalFix**：一个是"核弹级全拆"（会导致热失控、相机/充电被禁），一个是反例（改 `/vendor` + 全核 conservative）。都不适合做成产品功能。
- **不选 KernelAdiutor / SmartPack 作为实现来源**：两者均 archived，代码是 2016–2020 年的 Java 8 风格，且 GPL-3.0，与 HazeRoot 的"不直接复制代码"要求冲突。
- **不选 MiThermalTuner 作为代码来源**：GPL-3.0 + Shell/awk 实现（设备端纯 awk 做 AES），移植到 Java 反而要重写；但它的 `docs/thermal-config-format.md` 是目前**最完整的 mi_thermald 配置格式文档**，作为"知识来源"价值最高。
- **不选 Thanox**：Apache-2.0 友好，但主体是应用/进程管理，未验证到专门的温控/刷新率实现，借不到东西。
- **不选 franco/EX Kernel Manager**：闭源，GitHub 上只有本地化仓库。

### 5.3 最小可行实现路径（MVP，可直接开工）

#### 温控模块（建议 3 个 Tab：概览 / 限制 / 高级）

**Step 1｜数据采集（一条 shell，别开 100 个进程）**

```bash
su -c '
for z in /sys/class/thermal/thermal_zone*; do
  [ -e "$z/type" ] && echo "ZONE|${z##*/}|$(cat $z/type)|$(cat $z/temp)"
done
for c in /sys/class/thermal/cooling_device*; do
  [ -e "$c/type" ] && echo "COOL|${c##*/}|$(cat $c/type)|$(cat $c/cur_state)|$(cat $c/max_state)"
done
for p in /sys/devices/system/cpu/cpufreq/policy*; do
  echo "CPU|${p##*/}|$(cat $p/scaling_cur_freq 2>/dev/null)|$(cat $p/scaling_max_freq 2>/dev/null)|$(cat $p/cpuinfo_max_freq 2>/dev/null)"
done
echo "GPU|$(cat /sys/class/kgsl/kgsl-3d0/devfreq/cur_freq 2>/dev/null)|$(cat /sys/class/kgsl/kgsl-3d0/devfreq/max_freq 2>/dev/null)"
echo "BATT|$(cat /sys/class/power_supply/battery/temp 2>/dev/null)|$(cat /sys/class/power_supply/battery/capacity 2>/dev/null)"
echo "TSTATE|$(cat /sys/class/thermal/thermal_message/temp_state 2>/dev/null)"
dumpsys thermalservice | head -120
'
```

一次 `su` 拿到全部；解析沿用 FrameX 的 `ThermalServiceParser` 逻辑（移植到 `core/thermal/ThermalDumpParser.java`）。

**Step 2｜状态展示**
- 温度：`zone.temp/1000`（用 KernelAdiutor 的"2 位数判定"纠偏，别硬除 1000）
- 是否正在被限：`cooling_device.cur_state != 0` 列表 + `Thermal Status: N`（0=NONE 最健康，≥3 已严重）
- 频率：`scaling_cur_freq` vs `cpuinfo_max_freq` 的百分比条

**Step 3｜三个开关（按风险从低到高，默认全关）**

```bash
# L1 低风险：框架热状态覆盖（1 分钟生效期，可随时 reset）
cmd thermalservice override-status 0     # 关；恢复用 cmd thermalservice reset

# L2 中风险：CPU/GPU 直控上限
echo 1516800 > /sys/devices/system/cpu/cpufreq/policy4/scaling_max_freq
echo 315000000 > /sys/class/kgsl/kgsl-3d0/devfreq/max_freq
# 恢复：回读 cpuinfo_max_freq / available_frequencies 最大值写回

# L3 高风险：小米场景配置覆写（仅当 /data/vendor/thermal/config 存在时显示）
#   读取 /vendor/etc/thermal-*.conf → AES 解密 → 编辑 trig/clr/target →
#   加密写 /data/vendor/thermal/config/ → setprop ctl.restart mi_thermald →
#   校验 /data/vendor/thermal/decrypt.txt
```

**Step 4｜"恢复原厂"**：一次执行 `cmd thermalservice reset` + 各节点写回 `cpuinfo_max_freq` + 删除 `/data/vendor/thermal/config/thermal-*.conf` + `ctl.restart mi_thermald`。这条路径必须做成**开机自检**（防止用户改完忘了恢复导致持续高温）。

#### 高刷模块（单页：模式列表 + 三个按钮）

**Step 1｜枚举**

```java
Display d = ((DisplayManager) getSystemService(DISPLAY_SERVICE)).getDisplay(Display.DEFAULT_DISPLAY);
for (Display.Mode m : d.getSupportedModes()) { /* modeId, refreshRate, physicalWidth/Height */ }
```
按 `Math.round(refreshRate)` 去重（同一 Hz 可能有多个 mode，如 120Hz/120Hz@360vsync）。

**Step 2｜锁定（三级回退，全部失败才报错）**

```java
// ① Android 14+ 首选：cmd display（用物理分辨率 + 整数 fps 匹配）
exec("cmd display set-user-preferred-display-mode " + w + " " + h + " " + fps + " 0");

// ② 厂商 settings（小米/HyperOS 必须补，否则被 LTPO 自适应吃掉）
exec("settings put system peak_refresh_rate " + fps + ".0");
exec("settings put system min_refresh_rate "  + fps + ".0");
if (isXiaomi) exec(
    "settings put secure miui_refresh_rate " + fps + ";"
  + "settings put secure user_refresh_rate " + fps + ";"
  + "settings put system plugin_refresh_rate " + fps);

// ③ 兜底：SF 事务码（索引从 dumpsys display 解析，取不到才 modeId-1）
exec("service call SurfaceFlinger 1035 i32 " + sfIndex);
```

**Step 3｜验证（一定要做，否则用户以为成功了）**

```bash
dumpsys display | grep -m1 -E 'renderFrameRate|mActiveModeId|sfModeId'
# 或小米：cat /sys/devices/virtual/mi_display/disp_feature/disp-DSI-0/dynamic_fps
```

**Step 4｜恢复**：`cmd display clear-user-preferred-display-mode 0` + `settings delete system peak_refresh_rate` / `min_refresh_rate` + 小米三个 key `delete`。

### 5.4 与 HazeRoot 现有架构的对齐建议

按 `HazeRoot-ARCHITECTURE.md` 的分层约束（`ui → domain → data`，`core` 独立，单类 ≤300 行）：

```

                 SfModeIndexResolver.java    // dumpsys display 解析 sfModeId
domain/usecase/  ThermalControlUseCase.java  // 读→展示→写→校验→回滚，FSM
```

### 6.2 GPL 项目里"能拿"和"不能拿"的边界

这是本次调研最关键的一条实务结论：

**可以拿（属于事实/思想，不受版权保护）**
- sysfs 节点路径：`/sys/module/msm_thermal/parameters/enabled`、`/sys/class/thermal/thermal_message/temp_state` …
- 命令字符串：`setprop ctl.restart mi_thermald`、`service call SurfaceFlinger 1035 i32 N`、`cmd thermalservice override-status 0`
- 算法/参数：AES-128-CBC、key = iv = `thermalopenssl.h`、PKCS#7
- 配置格式：`[节名]` + `algo_type/sensor/device/trig/clr/target` 的语义
- 设计模式：三级回退、写后回读校验、"只写 `/data/vendor/thermal/config/`"

**不能拿（属于表达）**
- 任何 `.java` / `.kt` / `.sh` / `.cpp` 源码片段
- vtools 的 `MiuiThermalAESUtil.java`、`ThermalDisguise.kt`、`kr-script/**`
- MiThermalTuner 的 `module/lib/*.sh`、`module/bin/mtaes.awk`
- KernelAdiutor 的 `MSMThermal.java`（尽管是"节点清单"，代码结构仍是表达）
- BS-THERMAL 的 `common/service.sh`

**建议的工程纪律**
1. 在 `NOTICE` / 项目 README 里列出"参考项目 + 许可证 + 只借鉴了哪些设计点"，这是最省事的合规动作。
2. 借鉴 GPL 项目时，**先写自己的接口（`ThermalNode` 常量类 + 命令构造器），再按 AOSP 文档填实现**，不要边看 GPL 代码边写。
3. `HazeRoot` 若要公开分发，避免引入任何 GPL 依赖（包括 Gradle 依赖），否则会牵连整个 App。
